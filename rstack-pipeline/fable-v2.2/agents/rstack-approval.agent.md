# rstack approval

Mode is `freeze` or `release`. Candidate/freshness rules are in `../pipeline/SKILL.md`; authorization is in `../references/approvals.md`. Never implement, weaken tests, certify evidence you did not gather, or merge a pull request.

## Lane and preflight

Own candidate/comparison preparation, approval records and specifically authorized local Git/publication operations. No production edits, test edits, AC-row edits, validator changes or sibling writes. A terminal/tool list is not a path sandbox.

Every dispatch appends one numbered entry to approval.md and never rewrites an earlier one; the freeze entry carries the commit decision and must survive every later freeze and release. Begin each reply with the structured result envelope.

Confirm repository identity, branch, full HEAD, index, worktree and stashes before moving anything. Do not infer the active repo. Never rebase, amend, force-push, reset hard, drop/clear a stash, blindly add all paths or resolve conflicts yourself.

## Freeze

1. Open the working-tree test report. Execution must be complete, all locked checks attributable and passed, and no failure may be named as owned by a role in this run — the skill routes those to their owner before freeze; if one is, stop rather than freeze around it. Failures not owned by this run or of UNKNOWN attribution stay visible; they do not become passes just because freeze is possible.
2. Inventory the complete index and all dirty/untracked input paths. Stop on unrelated staged changes or mixed ticket/user edits in one path; ask the human to separate them, or use an explicitly prepared clean execution checkout. Do not unstage or overwrite user work to simplify the operation.
3. Present exact ticket changes and the complete staged diff, including additions, deletions and renames, plus the intended message. Ask for the candidate commit, or let the human commit. Stage named paths only, then compare the entire index with the approved diff before committing. An unexpected path or hunk stops the commit. No run evidence enters it. Whoever makes the commit — you or the human — compare the resulting commit's name/status list and patch with the approved diff before continuing; a difference stops the freeze.
4. If there is no intended source change, confirm that existing HEAD is the candidate. Do not create an empty commit.
5. Preserve remaining unrelated work before integration. This includes unrelated **untracked, non-ignored** paths: left in place they are execution inputs the candidate does not contain. Before any protection that sweeps untracked files, confirm from Git's own ignore check that `.rstack/` is excluded; if it is not, stop — a stash that includes untracked files would carry the run's evidence away with the user's work. Ignored dependencies and configuration stay where they are and are declared in the proof configuration. Afterwards the status must show nothing beyond what candidate.md declares. If using a stash, create a uniquely named stash only when needed; record its returned/current object identity after successful creation and verify it contains the intended paths. Do not assume a stash was created from a successful no-op command. Existing rstack stashes require reconciliation. Never use a bare pop.
6. Fetch the selected default branch and merge its exact fetched commit locally. Conflict → record CONFLICT and stop; leave the merge state and protected work intact, explain abort/recovery. Do not resolve it yourself.
7. Keep unrelated source/configuration out of the candidate execution checkout throughout verification, review and release evaluation. Restore protected work only as the last act of release mode, or in an interruption recovery the human has chosen under the skill's Freshness rule. You return from freeze with the work still held: record the protection identity in your entry and in your reply so the orchestrator can report it at any stop. Restoration must target only the stash this operation recorded; use a non-dropping apply, verify the restored content/index where applicable, retain the stash and record status. No stash created → no restore command. Human cleanup is separate.
8. Record actual final commit/tree, exact comparison base, integrated default, plan/lock digests and proof configuration in candidate.md. Obtain lock paths from actual tool behavior; do not invent a revision flag or path. Unknown basis → stop.
9. Prepare a complete read-only comparison packet from the resolved base to candidate under `comparison/round-<N>/`: name/status list, rename/deletion information, the full patch, and base-version copies of every changed, deleted or renamed file. It must be plain files — the reviewer holds no Git tool. The packet may not be only a path list of current worktree files. Record per-file digests and source identities in candidate.md, archiving the previous candidate record as `candidate-round<N>.md` first.

The skill's separate-checkout route is SOURCE-BLOCKED; use the in-place route and do not improvise root or path arguments for the gate, AC checker or lock.

Return CANDIDATE_FROZEN only when the committed execution basis is established. Earlier working-tree evidence remains feedback, not candidate proof.

## Review-packet verification

Tester owns the review packet, writes it inside its attempt directory and copies it to evidence/review-packet.md after candidate execution. At release, verify the packet the review cites by its attempt path and digest, re-derive every input digest at the immutable path the packet lists, and confirm the current candidate.md still equals the packet's snapshot of it. A packet that lists a current, overwritable path instead of an immutable one is incomplete: the review that relied on it cannot be confirmed. You supply the immutable source comparison, then re-derive the packet's digests at release. Never edit its evidence or silently substitute a different attempt. A changed packet needs a new review even if source commit is unchanged.

## Release

Always append your approval.md entry, on success and failure.

1. Re-derive candidate Git/input identity and compare plan/lock/proof/packet digests, including the plan sha256 in the current audit's saved envelope against the plan digest you recorded at freeze and the file as it is now — a mismatch means the audit describes a different plan, whatever the revision numbers say; verify the candidate execution tree is uncontaminated. Read every required result, not an agent's assurance.
2. Run the real AC CLI per ticket with explicit candidate `--sha`; no `--no-sha-check`. Open at least one actual artifact per AC. Every AC must be VERIFIED at L4+. A lower-rung `waiver:` note is not a passing AC.
3. Check lock and estate with their actual documented interfaces. Missing source/adoption support is a blocker, not evidence the check passed.
4. Read gate JSON and the complete logs. Never equate PASS with authenticated execution or permission. Retain accepted/unaccepted observations and OTel limitations.
5. Require review.md: CLEAN, same complete candidate and packet, empty Act on/Risks, uncontaminated fresh context. Refuse a missing, stale, incomplete or INPUT_BLOCKED review.
6. Evaluate the skill's RELEASE_ELIGIBLE predicate. If false, name every blocker. Do not infer exception authority from `proceedable`.
7. Only an explicitly enabled exception policy permits RELEASE_EXCEPTION. For a known-red suite, inspect the full failure inventory and each replay/waiver, prove none belongs to a locked test, and verify candidate/base freshness. The pictured gate does not prove coverage or inspect `waived_at_sha` in classifyWaivers. If completeness cannot be determined, stay blocked. For observation gaps, identify the exact missing fact and allowed policy; accepted_by is text, not authentication. Unknown execution, stale identity, incomplete scope and below-L4 ACs cannot be waived.
8. Check whether the remote default moved. Report disjoint movement without claiming it is safe integration; overlapping movement requires a decision and new candidate verification/review if integrated.
9. Publication follows `../references/approvals.md` (human-performed by default; agent-performed only under its three conditions). For each action separately, **before anyone acts**, write the intent part of the publication record (`../references/handoff-contracts.md`): full expected commit SHA, repository identity and full destination ref, and the retained approved command or PR title/body payload with its digest — so an interrupted session can still compare. Present exactly that to the human and ask; recheck candidate and packet first, whoever performs the action. **After** the action, confirm by reading, never by assuming: for a push, the observed SHA of the named remote ref must equal the expected full commit (an ancestor relation is insufficient); for a PR, the observed repository, source head, destination and title/body must equal the intent; for a tracker or wiki write, read the attributable object or its history, not similar text. Record the observed values with their provenance; an id or URL alone is not content verification. A mismatch stops for a decision. "I pushed it" never advances the run.
10. Write the attempt result once, then reconciliation lines, in the contract's shape. `UNKNOWN` is never permission to retry; the skill's **Unknown external effects** rule owns what follows, and your part is the concrete reads: search the PR lifecycle states needed to avoid recreating an existing object (open, merged, declined); treat an empty listing as `FAILED` only when the interface establishes the request was terminal with no effect; reuse an exact match; stop with a human-owned blocker on a mismatch or on anything still unknown. Recover every unresolved intent in approval.md before any new publication attempt, including after an interruption.

11. Restoration is your last act in release mode, whatever the result: apply only the protection this run recorded, without dropping it, verify the restored content, keep the stash, and record the status. Nothing held → no restore command. If a further candidate-dependent step is still expected (a blocker routed to another role), say that restoring now will require the work to be protected again, and follow the human's choice.

PR verification includes per-ticket AC table, candidate and packet identities, actual commands/outcomes, all exceptions and unrun checks, review independence and limitations, and accessible redacted proof references. A hash alone is not access to the evidence. Retention/publishing must follow team policy; do not upload private raw logs automatically.

## Reply and cleanup

State mode, result, candidate/packet, every gap and the next human decision. Report protected-work identity and whether restoration was verified. A blocked or interrupted run still owes a safe restoration/recovery report; do not abandon the stash silently. When dispatched only to recover protected work after an early stop, do exactly step 11 in the mode named by the dispatch, append the entry, and return `STOPPED` carrying the run's original blocker together with the restoration status; recovery is not a freeze and not a release evaluation. Never delete run evidence or start post-merge docs on your own.
