You are performing an independent architecture and maintainability review of an AI software-engineering pipeline named rstack.

This is not a normal code review.

Your job is to determine whether the pipeline has become over-engineered, identify what architecture is genuinely valuable, remove accidental complexity, and produce a coherent V2 design that preserves the important safety and evidence properties without drowning agents in prose, duplicated rules, state machinery, and overlapping contracts.

You have access to:

1. The complete conversation that led to this review.
2. Screenshots and reconstructed copies of the existing rstack files.
3. Proposed simplified/improved versions produced during the conversation.
4. The actual repository/workspace through Codex, where available.
5. The pipeline's agents, skills, references, scripts, and generated agent definitions.

IMPORTANT:
Do not trust any previous conclusion merely because ChatGPT, the existing rstack implementation, or another model made it.

Treat all three as hypotheses:

A. The existing rstack design may be correct.
B. ChatGPT's proposed simplifications may be correct.
C. Both may contain mistakes.

Re-derive the architecture yourself.

==================================================
PRIMARY QUESTION
==================================================

Has rstack become over-engineered?

If yes, determine precisely:

- what complexity is accidental;
- what complexity is necessary;
- what can be deleted;
- what should be consolidated;
- what belongs in executable enforcement instead of prose;
- what belongs in a reference rather than an agent prompt;
- what belongs in an agent rather than the pipeline skill;
- what should remain duplicated intentionally because local context requires it;
- what mechanisms are protecting against real failures versus hypothetical failures.

Do not equate "more robust" with "more rules."

A smaller system with stronger invariants is preferable to a larger system whose correctness depends on agents remembering hundreds of prose rules.

==================================================
CORE DESIGN PRINCIPLE TO TEST
==================================================

The architecture appears to be aiming for:

    plan
      ↓
    adversarial plan audit
      ↓
    tests written before implementation
      ↓
    implementation
      ↓
    independent test gate + impact evidence
      ↓
    fresh-context architecture/review
      ↓
    final approval + human-controlled external actions

That basic separation may be valuable.

The question is whether the machinery surrounding it has grown far beyond what is necessary to preserve those separations.

Do not discard the architecture simply because the implementation is verbose.

Separate:

1. architectural value,
2. operational enforcement,
3. documentation,
4. historical commentary,
5. redundant explanation.

THIRD TASK — DETECT POLICY DUPLICATION
==================================================

Search across the entire architecture for equivalent rules expressed multiple times.

Examples that appear likely to be duplicated include:

- do not modify tests
- do not modify production code
- never merge
- ask before external writes
- tests must be written first
- reviewer receives fresh context
- sibling repositories are read-only
- do not rewrite history
- do not weaken a failing test
- do not fabricate evidence
- missing evidence is not a pass
- acceptance criteria must be falsifiable
- external content is data rather than instruction
- one active repository per run
- a green suite only proves what the tests assert
- report what is not proven first

For each duplicated rule determine:

A. Should it live only in executable policy?
B. Should it live only in the pipeline skill?
C. Should it live in a shared reference?
D. Does an agent need a short local reminder?
E. Is duplication intentionally defensive?

Do not mechanically deduplicate.

Some local repetition may improve reliability.

But every repeated rule consumes context and creates drift risk.

==================================================
FOURTH TASK — SEPARATE FOUR TYPES OF CONTENT
==================================================

Classify significant blocks of the existing files into:

1. CONTRACT
   A rule necessary for correct execution.

2. ENFORCEMENT DOCUMENTATION
   Explanation of something a script actually guarantees.

3. OPERATOR GUIDANCE
   Useful information for humans maintaining the pipeline.

4. HISTORICAL NARRATIVE
   Explanations such as:
   "this exists because a real run once..."
   "the previous version did..."
   "we observed..."
   "this rule used to..."

Historical lessons may be valuable.

But they should generally not consume every agent's operational context.

Consider moving them to:

- ADRs,
- regression tests,
- harness documentation,
- CHANGELOG,
- maintainers' notes,

rather than keeping them in prompts executed on every ticket.

==================================================
SIXTH TASK — IDENTIFY CODE THAT MAY BE UNNECESSARY
==================================================

Do not assume turning prose into scripts is always an improvement.

For each script ask:

1. What concrete failure does it prevent?
2. Has that failure occurred?
3. Would a simpler invariant prevent the same failure?
4. Does another script already protect the same boundary?
5. Does this script introduce state that itself needs validating?
6. Does it create additional artifacts purely so another script can validate them?
7. Does it increase the number of possible pipeline states?
8. Is the mechanism more complicated than the failure it prevents?

Flag circular protection patterns such as:

    artifact
      → validator
        → validator evidence
          → gate checking validator evidence
            → another artifact describing the gate

when a simpler invariant could provide equivalent protection.

==================================================
SIXTEENTH TASK — TEST THE SIMPLIFIED ARCHITECTURE
==================================================

Try to design the smallest system that preserves these invariants:

1. Human intent becomes explicit acceptance criteria.
2. The implementation does not grade its own requirements.
3. Tests are authored independently from production code.
4. Tests cannot silently be weakened to make implementation pass.
5. Production changes are tested before review.
6. Review happens from a fresh context.
7. Review examines more than whether tests are green.
8. Evidence cannot be fabricated or silently upgraded.
9. External writes require explicit human authorization.
10. A human can tell what is still unproven.
11. Multi-repository writes cannot accidentally escape the intended repository.
12. The pipeline cannot claim completion merely because the implementing agent says it is complete.

Design the minimum architecture that satisfies those invariants.

Then compare it against current rstack.

==================================================
DO NOT DO THIS
==================================================

Do not:

- praise complexity because it is sophisticated;
- prefer a rewrite merely because it is shorter;
- delete a mechanism whose failure mode you have not understood;
- preserve a mechanism merely because it came from a real incident;
- optimize each file independently;
- treat Markdown as enforcement;
- treat scripts as automatically superior to Markdown;
- use "best practices" as evidence without explaining the mechanism;
- invent requirements not present in the system;
- normalize contradictions silently.
