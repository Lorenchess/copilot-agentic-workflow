# Worked example — PAYMENTS-12345 (testing, Phase 3, LARGE)

This directory is a **Phase 3 test-stage example** for the same fictional scenario `docs/examples/PAYMENTS-12345-planning/` planned: retrying a failed webhook delivery in `payments-api` with exponential backoff, and recording every retry attempt in `payments-ledger`'s existing audit log, per the plan's `I1` interface. It runs stages 0 through 5b of `.github/pipeline/FLOW.md` (Entry, Intake, Workspace, Plan, Adversary, Test RED, Test review) and stops at stage 5b **by design** — this is a D5-style boundary the example deliberately draws, not a failure. Stages 6–10 (Develop, Verify, PR draft, Publish, PR) are **not run** and produce no artifacts in this directory.

**Everything in this directory is fictional.** Every Jira key, repository name, file path, class, identifier, git SHA (40-hex placeholders, distinct from those used in `docs/examples/PAYMENTS-12345/`), and tool output line is invented for illustration. Where a fenced block presents tool output, it is captioned "fictional tool output" — no example in this directory claims that any command was actually executed.

**Non-validation caveat, toward both existing PAYMENTS-12345 directories.**
- Toward `docs/examples/PAYMENTS-12345/` (the completed Phase 1 reference run): that run's tests, verification, and publication do **not** validate the test contract built here, and this directory's test contract does **not** validate that run. The two directories use the same fictional Jira facts but were produced under different contract versions, independently.
- Toward `docs/examples/PAYMENTS-12345-planning/`: this directory consumes that directory's round-`1.2` PLAN.md **unchanged** — `PLAN.md` here is a byte-identical copy (verified with `git hash-object`; both files hash to `762b3c16f817acafea6f657782e6060bc4e685b8`). This directory does not re-plan, re-derive, or re-approve anything in PLAN.md; it demonstrates what Tester and Adversary (test-review mode) produce once that already-approved plan is handed to stage 5.

`payments-api` and `payments-ledger` are Java 17 / Maven / JUnit 5 / Spring Boot projects. `payments-ledger`'s tests already use an embedded PostgreSQL via `zonky`'s `embedded-database-spring-test` — fictional, stated so. `payments-api`'s tests already use H2 and a `MockWebServer` at the HTTP edge (simulating the merchant's webhook-delivery endpoint) — fictional, stated so.

2. `PLAN.md` — byte-identical copy of `docs/examples/PAYMENTS-12345-planning/PLAN.md`; read there for the full scope, evidence, and acceptance criteria this contract is built against (owner: `planner`, immutable input here).
3. `TEST-CONTRACT.md` — the round-2 (active) revision: Contract map for AC1–AC5/P1–P3 (AC5's three combined cases; AC2 at the boundary attempt `5 = maxAttempts`, plus the non-terminal attempt-4 row T14's boundary-value rule asks for), doubles limited to `MockWebServer` and `FakeClock`, the `I1` interface evidence table, the stage-5 Tester-origin adoption under Pre-existing test conflicts (with the bare `git diff` taken before any `git add`), the round-1→round-2 Correction rounds entry with the transition patch, envelope proof-relevance classified by inspection, relied-on existing test with its scoped command, and the full self-check (owner: `tester`).
4. `RED-REPORT.md` — the round-2 RED proof: the six-line T6 shape for every WITNESS, both runs, Preservation results including the relied-on baseline (owner: `tester`).
5. `TEST-REVIEW.md` — the round-2 (active) review: `ACCEPT`, with the round-1 `REVISE` finding (F1, the AC4 test's persistence double) recorded as resolved by the correction round (owner: `adversary`, test-review mode).
6. `SOURCE-EXCERPTS.md` — focused fictional Java/YAML excerpts (`FakeClock`; the AC1–AC3 and all three AC5 test bodies, including AC5(i)'s exact ledger-request assertion; the corrected AC4 test alongside its superseded round-1 version; the `I1` consumer-adapter test and its negative/deployment-compatibility counterpart, plus the provider-decoding assertions; the adopted pre-existing test before/after; and the `application-test.yml`/`pom.xml` fragments that justify the proof-relevance marks) — sufficient to assess the policy without a full checkout.

## What this example demonstrates

- A **stage-5 Tester-origin adoption**: constructing the contract surfaces a pre-existing `payments-api` test (`WebhookDeliveryServiceTest#failedDeliveryIsMarkedFailedAndNotRetried`) whose expectation ("no second attempt ever occurs") contradicts the now-approved AC1/AC2 retry behavior. Tester pauses stage 5 before any RED run or commit, records the conflict, `pipeline` voices the Tester-origin `TEST_CHANGE_REQUESTED` together with Tester's assessment, and, on approval, Tester applies only the approved delta, renames the test, and finishes stage 5 in the same invocation — the adopted file joins Protected paths at the round-1 RED commit, which is itself the anchor.
- A **5b `REVISE` → one automatic correction round → round-2 `ACCEPT`**, with a transition patch recorded from the superseded (round-1) anchor: the round-1 AC4 test doubled `AuditLogRepository` with a recorder instead of asserting through the real repository against the embedded PostgreSQL — a HIGH finding under T4's prohibition against doubling persistence when persistence is the required outcome. The correction touches only `payments-ledger`; `payments-api`'s anchor is unchanged.
- A **relied-on existing test** (`payments-ledger`'s `AuditLogRepositoryTest#persistsPaymentCapturedEventPayload`, covering P2) with its observed baseline result and the exact scoped runner command used to obtain it.
- **Proof-relevance decided by effect, never by file type**: `payments-api/pom.xml` is classified **no** (surefire and dependency versions only — no property selects what a contract test observes); `payments-api/src/test/resources/application-test.yml` and `payments-ledger/pom.xml` are classified **yes**, each with the property that makes it so.
- **`I1` interface evidence**: a consumer-adapter test asserting `RestLedgerClient`'s encoded JSON and path at the transport edge, a provider-decoding test (the corrected AC4 test) asserting the same fields, a `Conformance` value chosen honestly against what the two sides' evidence actually shows, and a dedicated negative/deployment-compatibility test that drives the real adapter against a failing transport response and discriminates it from the successful case (a successful report must not leave a false outstanding-report marker).
- **`FakeClock` determinism**: every test that asserts a scheduled delay or attempt timing names `FakeClock` in the Determinism column.
- **AC5's three combined cases**: re-report alongside the next attempt, evidenced by the dedicated ledger `MockWebServer`'s request count and the decoded content of its recorded requests, never a domain double; `PERMANENTLY_FAILED` together with the unreported-attempt marker, asserted in the same always-rejecting-ledger scenario rather than delegated to a separate test; `DELIVERED` before the report is recorded — each its own test, each observing the new `ledgerReportStatus` value only through its representation.
- **AC2 at the boundary attempt** (`5 = maxAttempts`) as its own row, distinct from the non-terminal attempt-4 row that shows the delivery is *not* yet terminal one attempt earlier.
- **Controlled "no further work" checks**: AC2's boundary, AC3, and both of AC5's terminal-marker cases each drive `FakeClock` well past the largest possible delay and call the existing entry point once more, confirming no further merchant request, no further ledger report, and no pending scheduled attempt — never relying on a test driver's own iteration limit as evidence of stopping.

## What this example does not demonstrate

No amendment occurred in this run — the one test-change event here is the stage-5 Tester-origin **adoption**, which is a distinct route (T12) recorded under TEST-CONTRACT.md's Pre-existing test conflicts, not under Amendments. Consequently this example shows **no candidate anchor** in the amendment sense and **no completed activation transition** — activation applies only to an amendment or a recovery entry; an amendment can follow an accepted stage-5b review, but this run simply has none (see `tester.agent.md`'s Activation mode section and its Scope paragraph) — and **no re-review round tagged `-a<n>`** (that suffix is reserved for a re-review after an amendment). There is likewise **no coverage gap and no `NOT_VERIFIED` clause** in this run — every clause's required level executes locally against H2, the embedded PostgreSQL, or `MockWebServer`, so `.github/skills/test-contract/SKILL.md`'s T10 machinery (equivalent/partial evidence, `RUNNER_UNAVAILABLE`, authorized exceptions) is not exercised here; see `TEST-CONTRACT.md`'s Coverage gaps section and T10/T12 in the skill for where those rules live. The round-1→round-2 anchor transition here is a **stage-5b correction round**, not an amendment: per `tester.agent.md`'s Activation mode Scope paragraph, a correction-round commit "replaces an anchor no review has accepted, and is recorded as the anchor directly" — there is no activation step to invoke.
