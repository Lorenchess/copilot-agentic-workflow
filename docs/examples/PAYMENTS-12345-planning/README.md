# Worked example — PAYMENTS-12345 (planning-only, Phase 2)

This directory is a **Phase 2 planning-only variant** of the PAYMENTS-12345 / PAYMENTS-12351 scenario, demonstrating the richer Planner → Adversary → G3 planning contract added in `docs/specs/2026-09-10-phase-2-planning-quality-contract.md`. It runs stages 0–4 of `.github/pipeline/FLOW.md` (Entry, Intake, Workspace, Plan, Adversary) and stops at gate **G3 — Plan approval**. Stages 5–10 (Test through PR) are **not run** and produce no artifacts in this directory.

**This is a separate directory from, and does not modify, `docs/examples/PAYMENTS-12345/`.** That directory is the completed Phase 1 reference run (all eleven artifacts, byte-identical, unchanged) and remains the illustration of the full pipeline. This directory exists only to show what a Phase 2 Planner and Adversary produce under the new rules (`R1`–`R10`), for the *same* fictional scenario, reusing its Jira facts, identifiers, and repository evidence — it is not a re-run or an update of that completed example.

**Non-validation caveat.** The Phase 1 run's tests (TEST-CONTRACT.md, RED-REPORT.md), verification (VERIFICATION.md), publication (WORKSPACE.md's Publish section), and developer approvals in `docs/examples/PAYMENTS-12345/` do **not** validate the plan in this directory. This directory's PLAN.md is a different, richer plan (repository evidence, change class, an interface row, testability fields, a re-routed decision, and a newly cited consumer the Phase 1 plan never mentioned) reviewed and approved on its own terms by this directory's own ADVERSARY-REVIEW.md and G3 entry. Nothing here claims that Phase 1's completed delivery proves this plan correct, and nothing here claims this plan's approval retroactively validates Phase 1's delivery. The two directories are independent illustrations of two different contract versions applied to the same fictional facts.

**Everything in this directory is fictional.** Every Jira key, issue, and field value; every repository name, file path, and code description; every identifier (`E1…`, `I1…`, `Q1…`, `AC1…`, `P1…`, `RK1…`) is invented for illustration, as in `docs/examples/PAYMENTS-12345/`.

## Reading order

1. `RUN.md` — keys, repositories, branch, developer context, G1/G2 entries (same as Phase 1); Stage status table through stage 4 (stages 5–10 explicitly not run); Artifact history showing round `1.1` SUPERSEDED and round `1.2` ACTIVE for PLAN.md/ADVERSARY-REVIEW.md; the full G3 gate entry, voiced in the new wording directly from PLAN.md's Decision summary and ADVERSARY-REVIEW.md's verdict (owner: `pipeline`).
2. `INTAKE.md` — reused **verbatim** from `docs/examples/PAYMENTS-12345/INTAKE.md` (byte-identical), as the immutable input both this variant and the Phase 1 example plan against (owner: `intake`).
3. `PLAN.md` — the round-`1.2` (active) plan: Change class, Requested scope disposition with a requirement items table, Repository evidence with a `Searched:` line, Approach citing evidence ids and implementation constraints, Dependencies and interfaces (one cross-repository row), Affected files with confidence and evidence, Acceptance criteria with `Observed at`/Preconditions/Path and a Combined outcomes note, Preservation expectations, Risks, Decisions and open questions (four `G3` rows, two `ASSUMED` rows), Out of scope, Decision summary, and a Response to adversary findings resolving round `1.1`'s three findings (owner: `planner`).
4. `ADVERSARY-REVIEW.md` — the round-`1.2` review: an independent requirement derivation performed before reading PLAN.md's disposition, both independent checks (evidence verification; the consequence-driven boundary check — which, in round `1.1`, found the merchant-facing `WebhookDeliveryStatusController` consumer PLAN.md's round-`1.1` text had not cited, and which round `1.2`'s plan now cites), the combined-outcome check, findings (three RESOLVED, one LOW residual), and a faithful Decision summary comparison (owner: `adversary`).

Every artifact carries the same six-field YAML header and the fixed section headings defined in `.github/pipeline/AGENT-CONTRACTS.md` and `.github/skills/plan-grounding/SKILL.md`/`.github/skills/challenge-plan/SKILL.md`, with inline provenance tags (`[JIRA]`, `[REPO]`, `[DEV]`, `[TOOL]`, `[INFERENCE]`) on every factual line.
