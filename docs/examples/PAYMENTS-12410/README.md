# Worked example — PAYMENTS-12410 (Phase 3, SMALL, through stage 5b)

This directory is a **Phase 3 worked example** for a fictional ticket, PAYMENTS-12410, "Reject non-HTTPS webhook endpoint URLs at merchant webhook registration." It runs stages 0–5b of `.github/pipeline/FLOW.md` (Entry, Intake, Workspace, Plan, Adversary, Test RED, Test review) and stops after stage **5b — Test review**, before Developer (stage 6) ever runs. Stages 6–10 (Develop through PR) are **not run** and produce no artifacts in this directory.

The planning-only version of this directory, stopping at G3, is the one recorded at tag `phase-2-reference` (`5a46eb7`); this directory extends it in place through stage 5b under the Phase 3 contract.

Where `docs/examples/PAYMENTS-12345-planning/` demonstrates the `LARGE` end of Phase 2's planning contract (a cross-repository interface, several `G3` decisions, a round-1.1-to-1.2 revision resolving three findings), this directory demonstrates the opposite end: a genuinely **`SMALL`** change, in a single repository, with no new or changed interface, no persistence or configuration change, and no unresolved material choice. It shows that Phase 2's richer contract does not force artificial weight onto a small change — PLAN.md here is short, Dependencies and interfaces is `None — <reason>`, and ADVERSARY-REVIEW.md legitimately records an **APPROVE on round 1.1**, with zero findings, because the independent checks it performed actually found nothing to raise — not because those checks were skipped.

Extending the same point into Phase 3: where `docs/examples/PAYMENTS-12345-testing/` demonstrates the `LARGE` end of the test-contract-quality policy, this directory's TEST-CONTRACT.md, RED-REPORT.md, and TEST-REVIEW.md demonstrate the `SMALL` end — one level (`API`), one repository, no doubles, and a compact test review — for the same reason: nothing here is padded to look thorough, and nothing that matters is left out.

**What SMALL proportionality deliberately does not write here** (skill T14): no Interface evidence table (PLAN.md's Dependencies and interfaces is `None`); no boundary-value rows (Risk 1's `HTTPS://` case-insensitivity is exercised as a second input inside AC2's own test, not a separate row); no discretionary preservation beyond the one `P` row and AC2's existing-clause basis (skill T5 bases 1–2 only — basis 3, a modified-boundary discretionary test, was not needed here); no correction round (the initial test review was a clean `ACCEPT`). No adoption, amendment, activation, or coverage gap occurred in this run; the stage-5 adoption and a correction round are demonstrated in `docs/examples/PAYMENTS-12345-testing/`; no example demonstrates an amendment, activation, or coverage gap.

**Everything in this directory is fictional.** The Jira key, issue, and field value; the repository name, file paths, and code descriptions; every identifier (`E1…`, `Q1…`, `AC1…`, `P1…`, `R1…`); and every git SHA and tool-output excerpt (40-hex placeholders and fictional surefire/`git` lines, labelled as such, distinct from those used elsewhere in this repository) is invented for illustration, as in `docs/examples/PAYMENTS-12345/` and `docs/examples/PAYMENTS-12345-planning/`. This directory does not modify, and is independent of, either of those.

## Reading order

1. `RUN.md` — keys (a single primary key, no secondary), repositories (only `payments-api` recommended and selected), branch, developer context (`provided: false`), Stage status table through stage 5b (stages 6–10 explicitly not run), Artifact history (round `1.1` ACTIVE for the plan, round `1` ACTIVE for TEST-CONTRACT.md/RED-REPORT.md/TEST-REVIEW.md — no revise round, no correction round was needed), Decision log (`none`), the full G1–G3 gate entries (owner: `pipeline`).
2. `INTAKE.md` — the fictional Jira facts and repository recommendation this plan is grounded in (owner: `intake`).
3. `PLAN.md` — `Change class: SMALL` with the sentence stating every limiting condition holds; a two-item requirement table (one `IMPLEMENTED`, one `PRESERVED`); repository evidence including a `NOT_FOUND` row; `Dependencies and interfaces: None — <reason>`; two acceptance criteria (one NEGATIVE, one POSITIVE) plus one preservation expectation; one risk; one `ASSUMED` decision row; a short Decision summary (owner: `planner`).
4. `ADVERSARY-REVIEW.md` — an independent two-item requirement derivation, one obvious local check appropriate to `SMALL` work, one combined-outcome case, and a legitimate zero-finding `APPROVE` on round `1.1` (owner: `adversary`).
5. `TEST-CONTRACT.md` — a two-row-plus-one-`P` Contract map (`API` level throughout, Doubles `none`), the two Envelope entries classified by inspection of their fictional content (`pom.xml` not proof-relevant; `application-test.yml` proof-relevant because its datasource property selects the storage the tests read back from — by effect, never by file type), `Relied-on existing tests: none` with the honest reason, the anchor and staged-set record, and the four-line contract self-check (owner: `tester`).
6. `RED-REPORT.md` — the one WITNESS test's RED proof (skill T6's six-line shape), both PRESERVATION results, and the fictional surefire excerpt for both consecutive runs (owner: `tester`).
7. `TEST-REVIEW.md` — the outcome-first derivation of AC1/AC2/P1's incorrect behaviors from PLAN.md alone, the one compact review pass, and a legitimate zero-finding `ACCEPT` on round `1` (owner: `adversary`, test-review mode).
8. `SOURCE-EXCERPTS.md` — the fictional AC1 test method, `application-test.yml`, and `pom.xml` fragment that TEST-CONTRACT.md's Envelope classification and RED-REPORT.md's Failure locus rest on.

Every artifact carries the same six-field YAML header and the fixed section headings defined in `.github/pipeline/AGENT-CONTRACTS.md`, `.github/skills/plan-grounding/SKILL.md`/`.github/skills/challenge-plan/SKILL.md` (stages 3–4), and `.github/skills/test-contract/SKILL.md` (stages 5–5b), with inline provenance tags (`[JIRA]`, `[REPO]`, `[DEV]`, `[TOOL]`, `[INFERENCE]`) on every factual line.
