# Worked example — PAYMENTS-12410 (Phase 4, SMALL, through stage 7)

This directory is a **Phase 4 worked example** for a fictional ticket, PAYMENTS-12410, "Reject non-HTTPS webhook endpoint URLs at merchant webhook registration." It runs stages 0–7 of `.github/pipeline/FLOW.md` (Entry, Intake, Workspace, Plan, Adversary, Test RED, Test review, Develop GREEN, Verify) and stops after stage **7 — Verify**, by design. Stages 8–10 (PR draft through PR) are **not run** and produce no artifacts in this directory.

The planning-only version of this directory, stopping at G3, is the one recorded at tag `phase-2-reference` (`5a46eb7`). The stage-5b version, stopping before Develop GREEN, is the one recorded at tag [`phase-3-reference`](https://github.com/Lorenchess/copilot-agentic-workflow/tree/phase-3-reference/docs/examples/PAYMENTS-12410) (`20939cc`); this directory extends it in place through stage 7 under the Phase 4 contract (`docs/specs/2026-09-11-phase-4-implementation-quality-contract.md`).

Where `docs/examples/PAYMENTS-12345-planning/` demonstrates the `LARGE` end of Phase 2's planning contract (a cross-repository interface, several `G3` decisions, a round-1.1-to-1.2 revision resolving three findings), this directory demonstrates the opposite end: a genuinely **`SMALL`** change, in a single repository, with no new or changed interface, no persistence or configuration change, and no unresolved material choice. It shows that Phase 2's richer contract does not force artificial weight onto a small change — PLAN.md here is short, Dependencies and interfaces is `None — <reason>`, and ADVERSARY-REVIEW.md legitimately records an **APPROVE on round 1.1**, with zero findings, because the independent checks it performed actually found nothing to raise — not because those checks were skipped.

Extending the same point into Phase 3: where `docs/examples/PAYMENTS-12345-testing/` demonstrates the `LARGE` end of the test-contract-quality policy, this directory's TEST-CONTRACT.md, RED-REPORT.md, and TEST-REVIEW.md demonstrate the `SMALL` end — one level (`API`), one repository, no doubles, and a compact test review — for the same reason: nothing here is padded to look thorough, and nothing that matters is left out.

**What SMALL proportionality deliberately does not write here** (skill T14): no Interface evidence table (PLAN.md's Dependencies and interfaces is `None`); no boundary-value rows (Risk 1's `HTTPS://` case-insensitivity is exercised as a second input inside AC2's own test, not a separate row); no discretionary preservation beyond the one `P` row and AC2's existing-clause basis (skill T5 bases 1–2 only — basis 3, a modified-boundary discretionary test, was not needed here); no correction round (the initial test review was a clean `ACCEPT`). No adoption, amendment, activation, or coverage gap occurred in this run; the stage-5 adoption and a correction round are demonstrated in `docs/examples/PAYMENTS-12345-testing/`; no example demonstrates an amendment, activation, or coverage gap.

**Everything in this directory is fictional.** The Jira key, issue, and field value; the repository name, file paths, and code descriptions; every identifier (`E1…`, `Q1…`, `AC1…`, `P1…`, `R1…`); and every git SHA and tool-output excerpt (40-hex placeholders and fictional surefire/`git` lines, labelled as such, distinct from those used elsewhere in this repository) is invented for illustration, as in `docs/examples/PAYMENTS-12345/` and `docs/examples/PAYMENTS-12345-planning/`. This directory does not modify, and is independent of, either of those.

## What this example demonstrates

- **One round, one repository**: `payments-api`'s `MerchantWebhookRegistrationService` gets a case-insensitive `https` scheme check in its existing shared validation step, used by both create and update — confirming Q1's `ASSUMED` shared-step basis directly, not merely assuming it.
- **A compact handoff**: one contract iteration, one bracketed handoff attempt (`H1`: contract run plus full suite; no relied-on test, so no scoped run), allowance `C 1/6 · D 0/6 · H 1/2` — SMALL proportionality (skill IQ15) applied to stage 6.
- **A LOW-confidence Affected-files entry handled honestly**: `validation.properties` is declared planned-but-not-changed, because the existing validation step builds its field errors with inline messages and no message key exists to change; Verifier accepts this as delivered (the element it served — AC1's field-naming error — passes), not blocking, no NOTE.
- **A one-pass PASS with zero blocking findings**: every obligation (`Q1`, Out of scope) `HONORED`; the five contract identities (AC1 CREATE/UPDATE, AC2 CREATE/UPDATE, P1) all GREEN; immutability and envelope checks both empty.
- **IMPLEMENTATION.md's line count reported as a measurement** (skill IQ15's SMALL guidance, "about 30–35 lines... not a gate"), never treated as a pass/fail gate.
- The run **stops at stage 7 by design**: stages 8–10 are not run, and G4 is not asked.

## What this example does not demonstrate

No fix round: Verifier round 1 is `PASS` outright — no finding blocks, so there is no round 2 and no Fix-round response beyond `n/a`. No `PLAN-TRACED` path: the one changed production path (`MerchantWebhookRegistrationService.java`) is a plain Affected-files `PLANNED` entry — this example does not exercise IQ5's `PLAN-TRACED` trace-and-necessity route (see `docs/examples/PAYMENTS-12345-testing/` for that). No `ROLLOUT` obligation: a single repository, no cross-repository interface, so no deployment-compatibility disclosure — VERIFICATION.md's Disclosures line is `none`. No `IMPLEMENTATION_BLOCKED` STOP, no directed round, and no `BASELINE_FAILURE`, `DEFECT`, or `GAMING` finding — the one round completes cleanly within its allowance. No suite baseline was taken (GREEN evidence: "not taken (optional)"). As in the stage-5b run this directory extends, there is still no amendment, no activation, and no coverage gap.
