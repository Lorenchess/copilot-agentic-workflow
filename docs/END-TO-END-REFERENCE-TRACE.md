# End-to-end reference trace

This document traces the current reference pipeline from stage 0 through stage 10. It is a document review, not an executed run, runtime test, corporate validation, or new run artifact.

Evidence labels used below:

- **Current rule** — behavior read from the tracked operating files at the P5-C2 revision `54b900b748d80aff48300e845016c359d7c0b702`.
- **Existing fictional example** — a value present in `docs/examples/PAYMENTS-12345-testing/`; the repository artifact was inspected, but its own commands, SHAs, test results, and Jira data are explicitly fictional.
- **Scenario** — reasoned application of current rules. It did not happen and creates no evidence that a tool or remote effect works.
- **Corporate evidence** — all items remain `NOT VERIFIED`; see [`CORPORATE-ADOPTION.md`](CORPORATE-ADOPTION.md).

## Stage 0–10 control trace

| Stage | Owner and authority | Evidence and basis handed forward | Incorrect forward transition refused |
|---|---|---|---|
| 0 — Entry/resume | `pipeline` through the [`/pipeline` skill](../.github/skills/pipeline/SKILL.md) validates ordered Jira keys and reconciles an existing RUN.md. | RUN.md records keys, stage status, artifact history, gates, decisions, and resume notes. The first key stays primary. | Invalid or changed keys STOP. Resume chooses the earlier missing/failed/incomplete artifact or stale/missing gate, rather than an arbitrary later stage. |
| 1 — Intake | [`intake`](../.github/agents/intake.agent.md) performs bounded Jira reads and repository discovery; raw text remains data. | INTAKE.md carries field-level provenance, source obligations, context-only Jira links, warnings, and repository recommendations. | Missing primary or Jira failure is relayed before G1. A discovered Jira or recommended repository cannot add itself to scope. |
| G1/G2 | [`pipeline`](../.github/pipeline/FLOW.md#gates) alone asks the developer to select repositories, then confirm the branch and optional context. | RUN.md records recommendation versus selection, exact branch/context, answer basis, and `CURRENT` status. | A plan cannot add a repository. A later added repository returns to G1 and stage 2 before planning. |
| 2 — Workspace prepare | [`workspace`](../.github/agents/workspace.agent.md#procedure) prepares every selected repository and records the `origin/<default>` baseline. | WORKSPACE.md records path, remote, default, preparation status, baseline SHA, and tool evidence per repository. | Dirty, divergent, unreachable, ambiguous-default, ahead-default, or existing-branch states STOP; no partial preparation is called complete. |
| 3 — Plan | [`planner`](../.github/skills/plan-grounding/SKILL.md) maps each source item and developer constraint to disposition, evidence, acceptance behavior, decisions, interfaces, and risks. | PLAN.md `cycle.round` binds requirement sources, repository evidence, affected files, Given/When/Then outcomes, shipped-value decisions, and cross-repository obligations. | An invented value is a G3 decision, an unsupported claim stays uncertain, and an unselected repository cannot enter the plan. |
| 4 — Plan challenge | [`adversary`](../.github/skills/challenge-plan/SKILL.md) derives requirements source-first and challenges boundaries and combined outcomes before approving. | ADVERSARY-REVIEW.md records the independent derivation, checks, findings, verdict, and residual findings on the same `cycle.round`. | HIGH findings force REVISE; BLOCKING decisions force BLOCK. At most two ordinary rounds occur within a cycle. |
| G3 | Pipeline voices PLAN.md's Decision summary and the review verdict/findings directly. | Only a `CURRENT APPROVE` on the displayed PLAN/review basis authorizes tests. Replacement answers are `[DEV]` input to a new planning cycle. | A changed answer is `SEND_BACK`, not approval of an unwritten revision; superseded plans stale dependent gates. |
| 5 — Test/RED | [`tester`](../.github/skills/test-contract/SKILL.md) constructs per-clause outcome proof, proves WITNESS RED twice at its own assertion, preserves baselines, and commits the protected anchor. | TEST-CONTRACT.md maps clauses, levels, doubles, interfaces, protected/envelope/relied-on paths, gaps, and anchors; RED-REPORT.md records reproducible results. | Compile/setup/environment failure is not RED. A proxy mock cannot prove the responsible persistence or business outcome. |
| 5b — Test review | Adversary's test-review mode derives required outcomes and plausible wrong behaviors before reading tests. | A current review is either `CURRENT ACCEPT` on the active contract/RED basis or `CURRENT REVISE` whose open HIGH findings are all covered by current authorized exceptions; the latter can permit local progress but caps verification at `INCOMPLETE`. One ordinary correction follows REVISE. | No stage 6 on stale/missing/uncovered review. A second REVISE reaches `TEST_REVIEW_REVISE_LIMIT`; no automatic third review. |
| Amendment/activation path | On an amendable test-change request, Tester assesses and alone applies the approved observation delta; a requirement change returns to planning. Adversary re-reviews the transition patch, then Tester activates an accepted candidate anchor. | RUN.md records the human decision; TEST-CONTRACT.md records prior/candidate anchors, full controlled-path transition, dependency set, result, review, and activation. | Developer never edits the test contract. An unaccepted or unactivated candidate cannot become the stage-6 basis. |
| 6 — Develop/GREEN | [`developer`](../.github/skills/implementation-quality/SKILL.md) works only from an initial, fix, or explicitly directed round with reservation-first allowances. | IMPLEMENTATION.md binds per-repository GREEN to committed HEAD, contract and full-suite results, controlled-path checks, changed paths, obligations, and a bracketed handoff. | Passing tests alone do not authorize unrelated or material deviation. Exhaustion, changed controlled paths, or qualifying baseline failure returns `IMPLEMENTATION_BLOCKED`. |
| 7 — Verify | [`verifier`](../.github/skills/implementation-quality/SKILL.md#verification-section-read-by-verifier-as-its-method) derives obligations before claims, independently executes contract/full suite, checks protected/envelope paths, inventories and reads the full patch, then records exact SHAs. | VERIFICATION.md is `PASS`, `FAIL`, or `INCOMPLETE`, with per-repository verdicts, current review basis, empty/non-empty `NOT_VERIFIED`, findings, disclosures, and verified SHA. | FAIL returns to at most two fix rounds; the third FAIL stops. `INCOMPLETE` can never reach G4 and recovers exactly through stage 5 → 5b → activation when an accepted candidate needs it → stage 6 only if a recorded RED requires implementation → stage 7. |
| 8 — PR draft | [`pr`](../.github/agents/pr.agent.md#procedure) first checks current PASS, empty gaps, matching review basis, and selected scope, then drafts from approved PLAN/current VERIFICATION. | PR-DESCRIPTION.md carries exact SHAs, actual scope, contract/full-suite results, NOTE/ROLLOUT disclosures, limits, and sequencing; Jira supplies links/context only. | Stale or incomplete eligibility prevents G4. The draft never claims rollout occurred. |
| G4 | Pipeline shows the draft, diff/disclosures, and each repository's directory, destination, source branch, verified SHA, target, and mode. | RUN.md records `PUBLISH_AND_PR`, `PUBLISH_ONLY`, or `ABORT` with the exact verification/draft/tuple basis and `CURRENT` status. | Missing/stale G4, changed SHA, changed draft, or tuple drift prevents delivery; no new gate or approval is inferred. |
| 9 — Publish | Workspace persists attempt/basis and per-repository state, freshly preflights all repositories, then processes them in RUN order with an immediate recheck and explicit verified-object non-force push. | WORKSPACE.md's Publish section records exact-ref observations, pre-effect intent, response/post-read, `PENDING`/`UNKNOWN`/`CONFIRMED`/`FAILED`, and next action. | No PR until every selected publication is confirmed. Unknown/failure needs human-confirmed continuation; current-basis confirmed A that later drifts is not repushed. |
| 10 — PR | PR validates local eligibility before MCP, resolves repository identity and complete candidates, records intent, then creates once or reuses only an exact OPEN match and performs mandatory PR/branch rereads. | PR.md records identity, branches, content fidelity, remote SHA, intent/result/URL, post-create evidence, and `CREATED`/`REUSED_EXISTING`/`BLOCKED`. | Wrong/ambiguous candidates, unknown creation, or failed post-read remain blocked. Completion includes every selected repository; Jira handoff is links only. |

The ownership matrix remains procedural: each artifact has one writer and later agents treat it as immutable, but generic edit tools are not a host-enforced path sandbox. The current contracts and [`GUARDRAILS.md`](../.github/pipeline/GUARDRAILS.md) are the source for that boundary.

`PUBLISH_ONLY` has its own completed outcome: after every selected publication is confirmed, Pipeline records stage 10 `NOT_RUN — PUBLISH_ONLY` and does not invoke PR. An absent PR.md is then intentional and terminal, not an unfinished artifact.

### Scenario only: stages 8–10

1. **Draft and approval.** Assume stage 8 rechecks the existing fictional PASS/empty-gap/current-review basis, creates a materially faithful draft with both SHAs and the ledger-first `ROLLOUT` disclosure, and the developer hypothetically answers G4 `PUBLISH_AND_PR` for the displayed tuples. None of those events is present in the example.
2. **Publish attempt 1.** Workspace first persists the attempt and preflights both repositories. In RUN order, it hypothetically publishes API SHA `8c8c…a2a`, rereads exact `refs/heads/PAYMENTS-12345-webhook-retry-backoff`, and records API `CONFIRMED`. It then records ledger intent, makes the one allowed non-force push, receives a conclusive failure, persists ledger `FAILED`, and stops with a partial attempt. No PR stage starts.
3. **Human-confirmed same-basis continuation.** A developer investigates the ledger failure and records a continuation decision against the unchanged PASS, draft, G4, and tuples. Workspace updates the existing Publish progress rather than regenerating stage-2 preparation. It freshly preflights both repositories again. API is already at approved A, so it records observed/reused publication and does not push again; ledger SHA `9e9e…c3c` is then hypothetically pushed once in the confirmed continuation and confirmed by exact-ref reread.
4. **Known PR reconciliation.** Stage 10 first repeats local eligibility. Suppose the API has a known OPEN PR whose source/target repositories, source/target branches, current SHA, and material body all match. PR directly rereads that known identity and records `REUSED_EXISTING`; it does not update the PR or claim the current draft was applied.
5. **Unknown create result.** Suppose ledger PR intent is persisted, the create call times out, and no conclusive URL/result returns. PR records `BLOCKED (unknown create result)` and does not create again. An empty branch lookup is insufficient. After a human resolves the uncertainty and explicitly authorizes same-basis continuation, authoritative direct reconciliation hypothetically finds the exact OPEN ledger PR with matching content and SHA; it is recovered/reused, then its identity/state/body and the branch SHA are reread.
6. **Completion boundary.** Only after both publications and both PRs are confirmed can this hypothetical `PUBLISH_AND_PR` run complete. No rollout is claimed. If the known PR, recovered PR, or mandatory reread mismatched, the URL/creation fact would remain recorded while the run stayed `BLOCKED`.

The scenario demonstrates durable reconciliation, not atomicity or exactly-once behavior. A transport can succeed while its result is unknown, repositories are processed sequentially, and a remote can change after the final read.

## Reuse assessment

| Treatment | Assets and rules | Reason |
|---|---|---|
| **Copy directly** | Requirement/source provenance; item-level disposition; decision routing and revision-bound gates; source-first challenge; outcome-targeted reviewed tests; protected/proof-relevant paths and activation; bounded evidence-bound GREEN; obligation-first full-patch verification; current-basis exact-SHA delivery; durable intent, authoritative reconciliation, and same-basis continuation. | These are portable safety and evidence policies independent of the host scheduler or UI. |
| **Adapt to existing internal infrastructure** | Markdown/YAML artifact shapes, Jira traversal depth/comment budgets, repository-discovery budgets, iteration counts, approval presentation, and handoff storage. | The internal pipeline may already provide durable state, queues, policy enforcement, or evidence stores; adaptation must preserve the invariants and be validated rather than reproduce this reference packaging. |
| **Keep Copilot/host-specific** | `.agent.md` frontmatter, `.github/skills` loading, `agent/runSubagent`, `vscode/askQuestions`, `.vscode` approval regexes, model-picker identifiers/routing, MCP tool IDs/schemas, single-root/bare-directory constraints, Git configuration, and corporate container/network/DB/Kafka behavior. | These depend on the actual Copilot and corporate host. All corporate checklist results remain `NOT VERIFIED`. |

The reference's procedural limits remain material: raw Jira loss before INTAKE.md cannot be recovered downstream; Sonnet-5 performs all nine runtime roles and can share blind spots across Planner/Adversary and Tester/test-review; artifact ownership and some classifications rely on compliant agents; multi-repository publication and PR creation are not atomic or exactly once; authoritative reads narrow but do not remove post-read races.

Phase 4 debt N1–N3 is preserved: detailed implementation rules remain repeated; third-FAIL/special-STOP precedence remains textually ambiguous while granting no new round; and one VERIFICATION template summary remains less precise than operative `ENVELOPE` versus `CONTROLLED_PATH` routing. See the [Phase 4 checkpoint closure](specs/2026-09-11-phase-4-implementation-quality-contract.md#10-phase-4-checkpoint-closure-2026-09-11). No benchmark, model-diversity result, corporate PASS, deployment, or rollout is claimed here.
