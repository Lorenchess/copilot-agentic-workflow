# Comparison guide

This is the intended entry point for comparing this reference implementation against the organization's existing internal AI pipeline. It is not a marketing document and it does not claim this design is better — it is a checklist of specific, file-level design choices, paired with concrete questions worth asking about how the internal pipeline handles the same problem. Where this repository made a choice the internal pipeline handles differently (or doesn't need to handle at all, because its infrastructure already solves it), that is exactly the kind of thing worth surfacing in the comparison.

## Reading order

1. `.github/copilot-instructions.md` — the only rule that applies to every conversation in this workspace, not just pipeline runs.
2. The nine agents in `.github/agents/` — read each against its section in `.github/pipeline/AGENT-CONTRACTS.md`.
3. The three Phase 1 skills in `.github/skills/`, then the two Phase 2 policy skills, `.github/skills/plan-grounding/SKILL.md` and `.github/skills/challenge-plan/SKILL.md`, the Phase 3 policy skill, `.github/skills/test-contract/SKILL.md`, and the Phase 4 policy skill, `.github/skills/implementation-quality/SKILL.md`, read explicitly by `developer` and `verifier`.
4. `.github/pipeline/FLOW.md`, then `AGENT-CONTRACTS.md`, then `GUARDRAILS.md`, then `MODEL-ROLES.md` — in that order, since each later file assumes the vocabulary of the one before it. `MODEL-ROLES.md` carries the R12 Planner/Adversary independence section, the T16 Tester/test-review benchmark section, and the IQ16 Developer/Verifier benchmark section.
5. `.vscode/settings.json`.
6. `docs/examples/PAYMENTS-12345/` — the completed Phase 1 run; then the two Phase 2 planning-only views, `docs/examples/PAYMENTS-12345-planning/` and the tagged planning view of `docs/examples/PAYMENTS-12410/`; then the Phase 3 tagged views of `docs/examples/PAYMENTS-12345-testing/` (LARGE) and `docs/examples/PAYMENTS-12410/` (SMALL) through stage 5b; finally, their current Phase 4 versions, extended in place through stage 7 with IMPLEMENTATION.md and VERIFICATION.md.
7. `docs/END-TO-END-REFERENCE-TRACE.md` for the assembled stage 0–10 and failure trace, then `docs/CORPORATE-ADOPTION.md` for the separate host checks, all currently `NOT VERIFIED`.
8. The cross-cutting themes below, last — once every individual asset is familiar, the themes tie them together.

## `.github/copilot-instructions.md`

**What to look at**: the file is deliberately short (global rules only — trust boundaries, secrets, git safety, a pointer to `FLOW.md`) and contains no pipeline-specific rule (`docs/specs/2026-09-09-phase-1-core-pipeline-design-contract.md` §10 R1 acceptance required it stay under 60 lines with no pipeline-specific rule). It applies to every Copilot Chat conversation in the workspace, not just `/pipeline` runs.

**Questions to ask of the internal pipeline**:
- Does the internal pipeline have an equivalent "applies to every conversation" instruction file, or is trust-boundary guidance scattered per agent?
- How does the internal pipeline word its data-vs-instructions rule, and does it cover MCP tool responses explicitly, or only Jira/repository text?
- Where does the internal pipeline's secret-redaction rule live — a global instruction, a per-tool filter, or a runtime hook?
- Does a global instruction file risk being silently overridden by a more specific one, and if so, how does the internal pipeline order precedence?

## Agents (`.github/agents/*.agent.md`)

Each agent file below is read against its corresponding section of `AGENT-CONTRACTS.md`, which is normative for its `tools:` list and forbidden-operations list.

### `pipeline.agent.md`

**What to look at**: the orchestrator holds no terminal and no MCP tool at all (`tools:` in `pipeline.agent.md` frontmatter) — it only runs subagents, asks questions, and edits `RUN.md`. It is the only agent with `vscode/askQuestions`, because subagents are stateless and cannot ask the developer anything (documented explicitly in the agent body's Role and purpose section). Resumability is not a separate state machine: on `/pipeline <KEYS>` against an existing run directory, `pipeline` reads RUN.md and reconciles the requested key list against RUN.md's Keys — any mismatch is STOP `RUN_KEYS_MISMATCH`, raised before any resume point is even proposed — then lists which of the twelve artifacts are present, missing, incomplete, or failed, and proposes resuming at the earlier of the first missing/failed/incomplete artifact and the first gate in G1–G4 with no `CURRENT` answer (none recorded, or `STALE`), never an arbitrary later stage. RUN.md's Artifact history (artifact, stage, round, ACTIVE/SUPERSEDED, producing agent) is the record this reconciliation and the verifier both consult; redoing an artifact marks every later-stage artifact SUPERSEDED, and a SUPERSEDED artifact is never used as an input by any agent again — except `planner`, which reads the immediately prior PLAN.md/ADVERSARY-REVIEW.md revision as the prior plan on a revise round or a new cycle. Each gate answer in RUN.md's gates log also carries a basis (the exact artifact revision(s) the developer reviewed when answering) and a `CURRENT`/`STALE` status: superseding an artifact marks every gate answer whose basis names it `STALE` in the same edit, and a `STALE` gate is re-asked, recording a new `CURRENT` answer, before any later stage runs (contract A8).

Phase 2 extends what `pipeline` voices at gate **G3**: it is voiced directly from PLAN.md's Decision summary *and* directly from ADVERSARY-REVIEW.md (verdict, `cycle.round`, Residual findings) — not filtered through the Planner — and the answer is recorded as exactly one of `APPROVE`, `SEND_BACK`, or `ABORT`. Only a `CURRENT` `APPROVE` authorizes stage 5 (test authoring); an answer that accepts every displayed recommendation and changes nothing may be `APPROVE`, but any answer that changes approach, acceptance behavior, scope, or a material decision is recorded `SEND_BACK` with the per-choice answers tagged `[DEV]` — authoritative developer input, not approval of an unwritten plan. A `SEND_BACK` starts a **new planning cycle**: in the same RUN.md edit, the prior PLAN.md and ADVERSARY-REVIEW.md are marked SUPERSEDED and every gate answer whose basis names them is marked `STALE`, `planner` is invoked again reading the G3 entry as a `[DEV]` input, then `adversary`, then G3 is re-asked on the new `cycle.round`. A developer's redirection that adds a repository re-asks G1 for that repository (a new `CURRENT` G1 entry) and runs stage 2 for it *before* the new planning cycle starts — a plan never adds a repository itself. Because a send-back or redirect marks both prior planning artifacts SUPERSEDED in the same edit, and because WORKSPACE.md counts as *incomplete* whenever a repository in the CURRENT G1 selection lacks a `PREPARED`/`REUSED_EXISTING` status, an interrupted planning cycle resumes at stage 2 when a newly added repository is not yet prepared, at stage 3 when the replacement plan does not yet exist, and at stage 4 when the replacement plan exists but its review does not — never at stage 5 or later against a superseded plan.

Phase 3 inserts stage 5b between Test RED and Develop GREEN: `pipeline` invokes `adversary` in test-review mode with a prompt scoped to exactly that mode's inputs — PLAN.md, TEST-CONTRACT.md, RED-REPORT.md, the controlled paths, and, on a re-review, the amendment or recovery entry's approved delta and transition patch — never INTAKE.md, RUN.md, IMPLEMENTATION.md, ADVERSARY-REVIEW.md, `plan-grounding`, or `challenge-plan`. The run now produces **twelve** artifacts (TEST-REVIEW.md added) and two new STOP codes, `TEST_REVIEW_REVISE_LIMIT` and `VERIFICATION_INCOMPLETE`, with every existing STOP message unchanged. Stage 6 cannot start, and G4 cannot be asked, without a current test review or while VERIFICATION.md is `INCOMPLETE`; recovery from `INCOMPLETE` always returns to the earliest missing evidence — stage 5, then 5b, then stage 6 only if a recorded RED requires it, then stage 7 again — never to stage 7 alone, stated identically here, in `FLOW.md`, and in `skills/pipeline/SKILL.md`. On any `TEST-CHANGE-REQUEST` (Tester-origin at stage 5 or Developer-origin at stage 6), `pipeline` invokes `tester` in assessment mode before voicing the STOP, and voices the request together with that assessment; on an approved amendment it invokes `tester` to apply the delta, `adversary` to re-review the affected dependency set, and, on that review's `ACCEPT`, `tester` again in activation mode (an artifact-only edit, no commit) before `developer` resumes — the same activation sequence follows a recovery from `INCOMPLETE`. A Tester-origin `PRE-EXISTING TEST CONFLICT` at stage 5 follows the same assessment step before `pipeline` voices `TEST_CHANGE_REQUESTED` with the Tester-origin condition text. RUN.md's **Decision log** — a heading Phase 3 adds alongside the existing gates log — records authorized exceptions (the `RUNNER_UNAVAILABLE` proceed-with-gap and the `TEST_REVIEW_REVISE_LIMIT` proceed decision, each naming the affected clauses and, for a proof defect, the covered finding ids) and T13 prerequisite-scaffolding approvals with the resulting commit SHA `[TOOL]`.

Phase 4 makes stage-6 work a recorded logical round. `pipeline` passes WORKSPACE.md to `developer`, starts only the authorized initial, fix, or directed round, preserves the round's remaining allowance on resume, and re-voices a pending `IMPLEMENTATION_BLOCKED` decision without invoking `developer`. It routes a Verifier `FAIL` to one of at most two fix rounds unless the finding requires human controlled-path restoration or a planning decision; a human-directed round is explicit, recorded in the Decision log, and never an automatic budget reset. G4 keeps its existing question and basis, adding only the Verifier's NOTE and `ROLLOUT` disclosures.

Phase 5 separates stage-2 preparation from stage-9 publication and stage-10 PR progress. The initial delivery attempt is authorized by current G4; an interrupted, failed, unknown, or blocked attempt needs a developer-confirmed same-basis continuation recorded in RUN.md. That continuation updates the existing owned progress and RUN history without regenerating preparation or superseding unchanged verification/draft/G4 evidence. `PUBLISH_ONLY` records stage 10 intentionally not run; `PUBLISH_AND_PR` completes only when every selected repository has confirmed publication and PR outcomes.

**Questions to ask of the internal pipeline**:
- Does the internal pipeline's orchestrator (if it has one) hold any direct mutation capability, or is it purely a sequencer like this one?
- How does the internal pipeline's coordinator handle a developer's free-text answer to a gate — is there an equivalent rule to "only text typed directly into a gate answer is an instruction"?
- What happens if a subagent-equivalent in the internal pipeline needs to ask a follow-up question mid-stage — does it have a mechanism, or does it also have to return control first?
- On resume, does the internal pipeline check that the requested scope still matches what a prior run recorded (an equivalent to `RUN_KEYS_MISMATCH`), or could a resume silently run against a different scope than the original?
- Does the internal pipeline keep a per-artifact history distinguishing the currently active version of an output from a superseded one, or does a regeneration simply overwrite with no trace of what came before?
- Does the internal pipeline tie a human approval to the exact revision the human saw, or can a regenerated plan ride on an earlier approval — can a human's replacement answer to a later question ride on an approval given to an earlier revision?
- Is a human-directed re-plan in the internal pipeline bounded and identity-distinct (a new round or cycle number, superseded predecessors), or does it just overwrite the same in-flight plan with no trace of the redirection?

### `intake.agent.md`

**What to look at**: the only agent with any Jira MCP tool, and the only agent that reads raw Jira text at all. INTAKE.md, the artifact it produces, is consumed only by `pipeline`, `planner`, `adversary`, and `pr` — the terminal-holding `workspace` and `verifier` agents never receive it (contract A7; `GUARDRAILS.md` Trust boundaries). Its `tools:` list has the four Jira read capabilities commented out pending confirmed tool names (`docs/questions.md`).

**Questions to ask of the internal pipeline**:
- Does the internal pipeline isolate Jira-reading to a single agent/service, or do multiple components read raw Jira text?
- How does the internal pipeline resolve the "acceptance criteria" custom field across Jira instances where the field ID differs — by name search, like this repo, or a fixed field ID per instance?
- What happens when the internal pipeline's Jira integration is down mid-run — is there an equivalent to `JIRA_UNAVAILABLE`, and does it distinguish primary-key failures from secondary-key failures the way this design does?

### `workspace.agent.md`

**What to look at**: the only agent that creates branches or pushes — `tester` and `developer` commit only on the feature branch, never a new one and never to the remote — and it never reads Jira or repository *text* at all, not even INTAKE.md (contract A7: `workspace` is a terminal-holding agent and does not receive it). Its allowed git command forms are an explicit allowlist. At stage 9 it persists attempt/basis and per-repository intent before effects, freshly preflights all selected repositories, resolves the approved read/write repository identity, parses exact feature refs, then processes repositories in RUN order with an immediate recheck and explicit verified-object non-force push. Already-A is observed/reused without push; a current-basis confirmed A that later drifts is never repushed; partial outcomes remain durable and explicitly non-atomic.

**Questions to ask of the internal pipeline**:
- Does the internal pipeline have a single git-mutating component, or does more than one agent touch git directly?
- Is the internal pipeline's git command surface an allowlist (deny by default) or a denylist (allow by default, block specific verbs)?
- How does the internal pipeline prevent a push before its equivalent of a publish approval gate — a mechanical precondition check like this design's `G4_NOT_RECORDED`, or a different control?

### `planner.agent.md`

**What to look at**: every acceptance criterion must trace to `INTAKE.md` or `RUN.md`'s developer context or explicit reasoning recorded in the plan itself (Forbidden actions: "inventing acceptance criteria not traceable to..."). The planner is read-only over repository code. PLAN.md's Requested scope disposition records, per requested Jira key (primary first), IMPLEMENTED / PARTIALLY IMPLEMENTED / EXCLUDED with the covering criteria or exclusion reason — every requested key must appear, or the adversary triggers a REVISE. Every acceptance criterion carries an explicit source class (`JIRA`, `DEV`, `DERIVED`, `PROPOSED`) rather than being presented as sourced when it is not; a `PROPOSED` criterion (a product decision the planner itself proposes) requires explicit G3 confirmation from the developer, never silent adoption. On a revise round, `planner` holds `edit/editFiles` in addition to `edit/createFile`, restricted to its own artifact, PLAN.md, only (contract A6).

Phase 2 (`docs/specs/2026-09-10-phase-2-planning-quality-contract.md`) adds a construction layer, normative in `.github/skills/plan-grounding/SKILL.md`, which `planner` reads explicitly at the start of its procedure — and reads *only* that skill, never `challenge-plan` (Inputs, Role and purpose: reading the adversary's own method "would weaken the separation between construction and challenge"). Requested scope disposition now carries an **item-level table**: every separable source obligation from a requested key's Acceptance Criteria and description, and every developer constraint from RUN.md's Developer context, gets one of `IMPLEMENTED` / `PRESERVED` / `EXCLUDED` / `UNRESOLVED`, appearing exactly once. **Change class** (`SMALL`/`MEDIUM`/`LARGE`) is declared with one sentence on consequence and uncertainty, never file or repository count — `SMALL` requires *all* of its limiting conditions (one repository, localized behavior, no new/changed interface, no persistence/configuration change, no permission/money/data-integrity consequence, no unresolved material choice) to hold, not most of them. **Repository evidence** rows are typed (`RESPONSIBLE_COMPONENT`, `ENTRY_POINT`, `INTERFACE`, `CONFIG`, `PERSISTENCE`, `CROSS_REPO_CALL`, `ADJACENT_TEST`, `NOT_FOUND`); a `NOT_FOUND` row means "not found by these searches in this scope" — never proof of absence — and states the consequence of that uncertainty. **Affected files**' operative table is file paths only, never a directory or component name; anything that cannot be named as a file goes under a separate, explicitly non-operative **Investigation notes** list, written as prose (a question plus an evidence id), never as a path shape the verifier's textual path match could read as operative. **Dependencies and interfaces** rows keep failure behavior (what the consumer does when the provider fails) and deployment compatibility (may the consumer ship first?) distinct from implementation order (development sequencing); an owner outside this run is recorded as an external dependency, and a G3 answer never authorizes another team's work. Each acceptance criterion's **Observed at** field names an existing exercise route, or states `NO EXISTING ROUTE`, which routes the prerequisite to a `G3` row rather than being satisfied by a future boundary. **Preservation expectations** (`P1…`) express intended unchanged behavior as intent, supported by evidence — they do not prove the baseline passes and do not override the tester's baseline-failure procedure. **Decisions and open questions** routes every consequential unresolved choice or material assumption to `ASSUMED` (technical, reversible, concrete consequence recorded), `G3` (developer decides; the recommendation is displayed, not consent), `BLOCKING` (planning cannot proceed on any honest proposal), or `OUT_OF_SCOPE`; the shipped-value rule lets a preserved, evidenced existing default or a supplied approved policy be cited rather than treated as a new decision, while inventing a value is always `G3`. **Risks** each carry a treatment (covered by an AC/P id, a decision id, an unresolved prerequisite, or `ACCEPTED (reason)`) rather than standing unresolved. **Decision summary** is the section `pipeline` voices at G3, written for the developer, not a reviewer re-deriving the plan.

**Questions to ask of the internal pipeline**:
- How does the internal pipeline enforce (or not) that every acceptance criterion is traceable back to a specific source, and does it distinguish a criterion the tool derived from one a human actually stated?
- Does the internal pipeline's planning step read existing code, and if so, is that read-only, or can the planner make exploratory edits?
- Does the internal pipeline track per-requested-ticket disposition (implemented, partially, excluded) the way `PLAN.md`'s Requested scope disposition does, or can a requested item silently fall out of scope?
- What happens on a revise round in the internal pipeline — is there a round limit, and who decides when it's exhausted?
- Does the internal planner record what it searched for and did not find, or does an absent search result simply read the same as "confirmed absent"?
- Does the internal pipeline distinguish a recommendation the tool displays from the developer's actual consent, or can a plan's proposed default ship unless someone objects?
- Can a plan in the internal pipeline add a repository to the run's scope on its own, or does that always require a separate, explicit developer decision?
- Does the internal pipeline separate "the change is small" from "the change is low-consequence," or does file count alone decide review depth?

### `adversary.agent.md`

**What to look at**: a dedicated, read-only, plan-only critic that can only render APPROVE / REVISE / BLOCK — it cannot edit the plan itself, and it cannot approve a plan with no acceptance criteria (Forbidden actions). It also checks that PLAN.md's Requested scope disposition covers every requested key in INTAKE.md/RUN.md and flags every `PROPOSED` acceptance criterion as needing an explicit G3 decision; a plan whose disposition omits a requested key is REVISE by rule, not by judgment call. Like `planner` and `verifier`, `adversary` holds `edit/editFiles` in addition to `edit/createFile` (contract A6), restricted to its own artifact, ADVERSARY-REVIEW.md only — a revise round updates the same file rather than needing a second one.

Phase 2 makes `adversary` the only reader of `.github/skills/challenge-plan/SKILL.md` (in addition to `plan-grounding`, the same construction rules `planner` builds against). Its method is **source-first**: it reads INTAKE.md and RUN.md *before* PLAN.md's Requested scope disposition and records an **Independent requirement derivation** of items and developer constraints independently, then diffs that derivation against the plan — this establishes fidelity to the captured inputs, not completeness against the original Jira (both roles read the same captured INTAKE.md/RUN.md). It then performs **two independent checks**, recorded even when nothing is found and with no quota of files or findings: a consequence-driven boundary question ("what relevant caller, consumer, configuration, invariant, or failure interaction would make this plan wrong even if its citations are true?"), which may select and inspect evidence the planner never cited; and a combined-outcome question ("could an implementation satisfy every listed criterion yet violate the requested business behavior?"). It then works a **challenge catalogue** (missing requirements, invented scope, unsupported or misrouted assumptions, untestable criteria, missing failure paths and combined outcomes, cross-repository inconsistency, backward-compatibility gaps, unacknowledged operational risk, plan-to-repository mismatch, unnecessary complexity, unclear proposed decisions, Decision summary fidelity), each category carrying its own evidence expectation for what must actually have been checked before recording "no finding." Findings have a fixed shape (id, category, severity, evidence, what the plan must show or decide); severity drives the verdict mechanically — any HIGH forces REVISE, a `BLOCKING` row in Decisions and open questions forces BLOCK by rule regardless of other findings, and APPROVE requires no open HIGH and every MEDIUM either fixed or listed as a **residual finding**. A **zero-finding APPROVE is explicitly legitimate**: it records that the independent checks were actually performed, with no requirement for a novel finding and no count-based sentence ("N findings raised") standing in for evidence of independence. A finding may include a concise counterexample or a bounded alternative to explain itself, but `adversary` never authors or proposes a competing full plan. On a later round or cycle, it reviews PLAN.md's Response to adversary findings and re-raises any rejection lacking evidence-backed rationale.

Phase 3 adds a second mode, test-review (stage 5b): `adversary` reads the `test-contract` skill's construction rules, then its Challenge section, and independently, read-only, challenges TEST-CONTRACT.md and RED-REPORT.md against PLAN.md and the actual test source. Its inputs are limited to PLAN.md, TEST-CONTRACT.md, RED-REPORT.md, and the controlled paths — it explicitly does not read INTAKE.md, RUN.md, IMPLEMENTATION.md, `plan-grounding`, `challenge-plan`, or its own ADVERSARY-REVIEW.md in this mode, because a prior plan approval is never evidence of test adequacy. The method is outcome-first: step 1 derives, per clause, the required observable outcome and plausible incorrect behaviors from PLAN.md alone, before test source is inspected; step 2 asks whether those incorrect behaviors would pass the actual test; step 3 works the skill's catalogue (map completeness, assertion target vs Observed at, boundary/doubles, level sufficiency, RED validity and setup, classification and clause relationships, preservation bases and relied-on baselines, negative/boundary/combined cases, determinism, interface evidence kind and conformance, discovery, the protected/envelope/proof-relevant split against the staged set, coverage-gap and equivalence honesty, and, on re-review, the transition patch and dependency set), each category carrying its own evidence expectation. Findings carry the same id/category/severity/evidence shape as plan-review mode. The verdict is `ACCEPT` or `REVISE` only — never `BLOCK`, since a block-worthy condition already has its own STOP — and any HIGH forces REVISE; a zero-finding ACCEPT with Checks performed recorded is again explicitly legitimate. TEST-REVIEW.md's Basis names PLAN.md's `cycle.round`, TEST-CONTRACT.md's revision (anchor SHA per repository, correction round, latest amendment id), RED-REPORT.md's revision, the coverage-gap set, and, on a re-review, the candidate anchor and transition patch assessed. One automatic Tester correction round follows an initial REVISE; a second REVISE raises `STOP [TEST_REVIEW_REVISE_LIMIT]`. Any correction, amendment, proof-relevant envelope change, coverage/limitation change, or PLAN.md supersession marks TEST-REVIEW.md SUPERSEDED and triggers a re-review — on an amendment, scoped to the affected dependency set the amendment entry names, not every test. TEST-REVIEW.md is the twelfth artifact, with fixed headings Verdict, Basis, Required outcomes and incorrect behaviors derived, Checks performed, Findings, Residual findings, Round.

**Questions to ask of the internal pipeline**:
- Does the internal pipeline have an adversarial-review step distinct from the planner, or does the same component plan and self-critique?
- Does the internal pipeline mechanically check that every requested ticket's disposition is accounted for, or could an item silently drop out between intake and implementation?
- What is the internal pipeline's bound on revise rounds, and what happens when it's exhausted — automatic escalation, or does the plan simply proceed?
- Is BLOCK (an unconditional stop) distinguished from REVISE (a fixable gap) in the internal pipeline, or is there only a single "needs work" outcome?
- Does the internal pipeline's review step read the original requirement source before or after reading what the plan claims it covers — and does that order actually matter to how it derives findings?
- Would the internal pipeline's reviewer record and defend a zero-finding approval, or does review output implicitly need to show some number of findings to count as having happened?
- Does the internal pipeline require the reviewer to inspect a boundary the planner didn't already cite, or can a review stay entirely within the evidence the plan itself selected?

### `tester.agent.md`

**What to look at**: the only agent, besides `developer`, that can edit files inside a repository — and only test files it created itself (Forbidden actions: "`git add` a path it did not create under a test directory"). It must prove RED for the acceptance condition itself, never by weakening a criterion (Procedure step 5, Forbidden actions). Every test is classified WITNESS (a missing-behavior test that must be proven RED before implementation) or PRESERVATION (a constraint expected to pass before **and** after implementation, never labelled RED); the bounded two-attempt correction rule applies to WITNESS tests only, and a failing PRESERVATION test is diagnosed, never categorically treated as a test defect: a test-defect diagnosis is corrected within the same two-attempt budget and re-proven PASS, while a baseline-failure diagnosis is retained unchanged, recorded `PRESERVATION_BASELINE_FAILED`, and returned to the developer to reclassify WITNESS, exclude, or abort — the expectation is never weakened merely to obtain PASS (contract A10). TEST-CONTRACT.md's Execution envelope per repository records the exact contract command, build/test configuration files, and helper/fixture paths the tests depend on, so the developer's later boundary for "may I touch this file" is explicit rather than inferred. Every assertion targets the observable business outcome — persisted state, a returned value, an emitted call's arguments, timing where it is the requirement — never a proxy such as an invocation count alone or an HTTP status alone (Forbidden actions; Assertion quality). Before every `git add`/`commit`, an index-scope check (`git status --porcelain=v2 --branch`, twice) requires the staged set to equal exactly the intended test files, or the agent does not commit.

Phase 3 makes `tester` read `.github/skills/test-contract/SKILL.md` explicitly at the start of every invocation — construction, assessment, and amendment alike — rather than carrying its own copy of the rules. The Contract map's Level column is chosen by the outcome the clause requires, never by ease of RED (T3's outcome table, with a one-line reason tied to Observed at); doubles follow "real inside, doubled at the edge, doubles observe or supply a Given" and its five prohibitions, with ordinary input stubs explicitly allowed even when they influence the result (T4). Classification stays per clause on the four ordered PRESERVATION bases (T5); where an `ADJACENT_TEST` already covers a clause, it is instead recorded under Relied-on existing tests, run at stage 5 through the runner scoped to that class, with its observed baseline `[TOOL]` result and the scoped command recorded. RED-REPORT.md's RED evidence keeps T6's six-line shape (Expected, Observed, Failure locus, Setup, Why this proves the clause is unsatisfied, Validity) and six validity rules, the contract command run twice consecutively with identical results, and a Confirmation line stating every contract identity was discovered and reproduced on the second run. The Determinism column names a control (clock, randomness, ordering, async, concurrency) only where the clause actually has one (T7). For every `I` row, Interface evidence keeps consumer-adapter evidence, provider-decoding evidence, and a `Conformance` value of `ESTABLISHED`/`DESIGN_CHECK_ONLY`/`NOT_VERIFIED` strictly distinct from local business evidence (T8). Protected paths now cover every file `tester` created — tests and support alike: fixtures, fakes, recorders, builders, fake clocks, test-profile configuration — while Envelope entries are each marked proof-relevant yes/no **by effect, never by file type**, and the staged-set `[TOOL]` record taken immediately before each commit is compared against Protected paths (T9). Where a clause's required level cannot execute here, `tester` seeks equivalent evidence first, else records `NOT_VERIFIED` under Coverage gaps and raises `RUNNER_UNAVAILABLE` per clause (T10). Amendments carry T12's effect enum — `REQUIREMENT_CHANGE` is never amendable, routing instead to a new planning cycle — and `tester` is the sole writer of any approved amendment delta, the single narrowing of its own locked own-files rule; the candidate anchor's content **transition patch** (`git -C <dir> diff <anchor>..HEAD -- <paths>`, plus its `--stat` companion — two forms new to `tester`'s allowed command list, but already matching existing `true` rules in `.vscode/settings.json`, which is itself unchanged, so neither prompts; only the runner does) must equal the approved delta and nothing else before `adversary`'s re-review accepts it and `tester`, re-invoked in **activation mode** (an artifact-only edit, no terminal command, no commit), records the candidate active. A stage-5 Tester-origin adoption of a pre-existing conflicting test instead uses the bare `git -C <dir> diff` output taken before any `git add`. Proportionality (T14) still scales every section by the SMALL/MEDIUM/LARGE change class carried over from Phase 2.

**Questions to ask of the internal pipeline**:
- Does the internal pipeline require acceptance tests to be proven RED before implementation, or does it allow test-and-implementation to happen together?
- Does the internal pipeline distinguish a "must fail first" test from a "must never regress" test the way WITNESS/PRESERVATION does, or is every test treated the same way?
- Does the internal pipeline record an execution envelope (config files, fixtures, the exact run command) as part of the test contract, or leave that implicit in CI configuration?
- How does the internal pipeline distinguish a legitimate RED (missing behavior) from a compile error or setup failure — is there a bounded correction-attempt mechanism like this design's two-attempt limit? What happens when the internal pipeline's equivalent of a never-regress test fails against the baseline — is that diagnosed and the failure preserved as evidence, or is the test simply adjusted until it passes?
- Does the internal pipeline require assertions on business outcomes specifically, or would an invocation-count or status-code-only assertion pass review?
- What happens in the internal pipeline when a written test passes on the first try — is there an equivalent to `TESTS_NOT_RED`, and who decides the outcome?
- Does the internal pipeline mechanically verify the staged git index before a test-authoring commit, or trust the tool/agent to stage only what it intended?

### `developer.agent.md`

**What to look at**: forbidden from ever editing a path listed in `TEST-CONTRACT.md`, or altering `TEST-CONTRACT.md` / `RED-REPORT.md` itself, under any circumstance — the only route to change a contract test is the `TEST-CHANGE-REQUEST` STOP, decided by the developer, executed only by `tester` (Procedure step 5, Artifact ownership rule). It may change a file in TEST-CONTRACT.md's execution envelope (for example, add a test-scope dependency) only when the implementation genuinely needs it, and every such change must be listed and justified under IMPLEMENTATION.md's Envelope changes ("none" when there isn't one) — changing an envelope file so a contract test becomes undiscovered, skipped, or excluded is forbidden regardless of justification. The same index-scope check as `tester`'s (staged set must equal exactly the intended files, checked immediately before both `add` and `commit`) applies here too.

Phase 3 sharpens what "the tests" means for `developer`: it must never edit a **controlled path** — a Protected path (every file `tester` created, including support: fixtures, fakes, recorders, builders, fake clocks, test-profile configuration), a proof-relevant envelope file, or a Relied-on existing test (skill T9) — and a file TEST-CONTRACT.md marks proof-relevant is never an ordinary envelope change, however well justified under IMPLEMENTATION.md's Envelope changes; only `tester`, through an approved amendment, may touch it. A `TEST-CHANGE-REQUEST` (either origin) now carries fixed content: the test identity; the assertion or setup at issue; the PLAN.md clause and evidence; the proposed change stated as an observation change; and an explicit statement whether the clause's required outcome is unchanged — because **an amendment may change how a test observes; it may never change what the approved clause requires** (T12's authority rule), and a request whose real effect is a `REQUIREMENT_CHANGE` is not amendable and instead starts a new planning cycle. Where TEST-CONTRACT.md records a clause `NOT_VERIFIED`, `developer` implements against PLAN.md's whole approved behavior for that clause, not only against the runnable tests — the absence of a runnable test is not license to implement less than the plan requires.

Phase 4 makes `developer` read `implementation-quality` in full before editing. GREEN now means a committed, bracketed handoff attempt on an unchanged clean HEAD: the exact contract command and every named identity pass, relied-on identities are observed, the full suite passes, both halves of the controlled-path check pass, the envelope diff matches declared changes, and the baseline-to-HEAD inventory contains no `UNRELATED` path. Each repository and execution is recorded reservation-first against the logical-round allowance. Paths are classified `PLANNED`, `PLAN-TRACED` with both an approved-element trace and necessity, `ENVELOPE`, `PROTECTED-TEST`, or `UNRELATED`; material deviation and four blocked conditions return to `pipeline`, and cross-repository work is handed off only when every repository is GREEN.

### `verifier.agent.md`

**What to look at**: executes **two** independent runs, both required for PASS, neither replacing the other — (A) the exact contract command from TEST-CONTRACT.md, confirming from the output that each named test identity was discovered, executed, not skipped, and produced its classified result (WITNESS now GREEN, PRESERVATION still GREEN), and (B) the repository's independently detected full suite/build, to prove no broader regression — rather than trusting `IMPLEMENTATION.md`'s GREEN claim for either (contract A4). It performs the test-immutability check (`git diff --stat <anchor>..HEAD -- <paths>`, anchored at the latest amendment or the top-level RED commit) as a mechanical command, not a judgment call, and a separate execution-envelope check (`git diff --name-status <anchor>..HEAD -- <envelope files>`) that treats an unjustified envelope change, or one that undiscovers/skips/excludes a contract test, as FAIL even when the test files themselves are untouched. It produces a changed-path inventory (`git diff --name-status <baseline>..HEAD`, from the baseline SHA WORKSPACE.md recorded) classifying every changed path as PLANNED, ENVELOPE, PROTECTED-TEST, or UNRELATED, and derives its diff-versus-plan and unrelated-change findings from that inventory rather than from reading current files alone. It also requires a clean checkout and records a candidate SHA before any test execution, then re-checks the checkout and HEAD afterward (FAIL, "checkout changed during verification", otherwise) — the SHA it records as verified is provably the state it actually tested, not just a HEAD read at some point during the run (contract A3).

Phase 3 keeps the test-immutability check's command form exactly as Phase 1 (`git diff --stat <anchor>..HEAD -- <paths>`) but widens its path input to Protected paths, now including every tester-created support file, and anchors it at the latest **activated** amendment when one exists. The execution-envelope diff now also covers Relied-on existing tests, and a change to a file TEST-CONTRACT.md marks proof-relevant is FAIL whenever no approved amendment covers it, regardless of any Envelope changes justification IMPLEMENTATION.md offers. `verifier` additionally requires observed execution of every relied-on identity — from the contract run, the full-suite run, or a scoped fallback run — treating a missing, skipped, or failing relied-on identity as FAIL. A new Test review basis check reads TEST-REVIEW.md's Verdict and Basis: a `CURRENT ACCEPT` whose Basis matches the ACTIVE TEST-CONTRACT.md/RED-REPORT.md revisions permits `PASS`; a `CURRENT REVISE` whose every open HIGH finding is covered by a RUN.md authorized exception caps the verdict at `INCOMPLETE`; anything else — missing, SUPERSEDED, or an uncovered REVISE — is FAIL. Verdict is now three-valued: `PASS` only when every check holds and the `NOT_VERIFIED` clause set (derived from TEST-CONTRACT.md's Coverage gaps plus RUN.md's authorized exceptions that are still **current** — a closed, re-reviewed gap's exception is history and drops out on its own) is empty; `INCOMPLETE` when every runnable check passes and the review-basis check holds but that set is non-empty; `FAIL` remains unchanged for any real failure, whatever exceptions exist.

Phase 4 adds an obligation-first, claims-last semantic review. Before reading the diff or IMPLEMENTATION.md, `verifier` derives `C`, `Q`, `I`, Out of scope, and `NOT_VERIFIED` obligations from approved inputs; it then inventories every changed path, reviews every hunk against plan scope, evaluates each obligation as `HONORED`, `VIOLATED`, `NOT_LOCATABLE`, or `ROLLOUT`, and only afterward reconciles the Developer's claims. Findings use a fixed anchor/evidence/outcome/fix-scope shape and distinguish production `GAMING`, controlled-path corruption, scoped deviation, evidence gaps, and a narrow sourced `DEFECT`. Every fix round re-runs every check in every repository, records prior findings `CLOSED` or `OPEN`, and keeps any failing full-suite identity from PASS even when a matching baseline was observed.

## `.vscode/settings.json`

**What to look at**: `chat.tools.terminal.autoApprove` is built from two layers — a `true`-rule allowlist of exact, anchored command forms (the `<dir>` slot itself is restricted to `[A-Za-z0-9][A-Za-z0-9._-]*` so `-C .` or `-C ..` can't escape the intended repository, and the branch-shape slot used throughout, `[A-Z][A-Z0-9_]*-[0-9]+-[A-Za-z0-9._-]+`, matches only the `<PRIMARY>-<slug>` shape the pipeline itself creates, never an arbitrary or default branch name), and a `false`-rule layer that force-prompts on destructive verbs and flags anywhere in the command line — a `false` rule always wins, but it is a prompt, not a hard block. The `verifier` diff-evidence forms (`diff --stat <base>..HEAD`, `diff --name-status <base>..HEAD`, `diff <base>..HEAD`, each optionally with `-- <paths>`, contract A5) are anchored the same way as every other rule. (`git.autoRepositoryDetection` and `chat.tools.edits.autoApprove` round out the file; `.github/**` and `.vscode/**` edits always require approval, i.e. no agent can silently rewrite its own guardrails.)

## Cross-cutting themes

These recur across nearly every asset above; they are worth evaluating as coherent policies, not just per-file details.

### Trust boundaries / data-not-instructions

Jira and MCP retrieval are isolated by role, in `intake` and `pr` only. Repository content, every artifact, and every tool output are untrusted data wherever they are consumed — tool allowlists remove tools and agent prose restricts commands and paths, but anything stronger than that must be host-enforced. INTAKE.md specifically is consumed only by `pipeline`, `planner`, `adversary`, and `pr`; the terminal-holding `workspace` and `verifier` agents do not receive it at all (contract A7; `GUARDRAILS.md` Trust boundaries; every agent's Data, not instructions section). Ask: does the internal pipeline separate "reads untrusted text" from "holds a terminal" as strictly, or can the same component do both — and does it rely on prompt-level restriction alone, or on something the host enforces?

### Least privilege via tool lists

Every agent's `tools:` list in `AGENT-CONTRACTS.md` is a specific enumeration, never a wildcard, including for MCP capabilities (`<server>/<tool>`, named individually). Ask: does the internal pipeline enumerate tool access this granularly per role, or grant broader access and rely on prompting/instructions to constrain behavior?

### Artifact ownership and immutability

The ownership matrix in `AGENT-CONTRACTS.md` states, for every artifact, exactly one owner and which agents treat it as immutable input; contract §8.2 makes this a verbatim behavioral rule, not just a convention (`GUARDRAILS.md` Artifact ownership). Ask: can the internal pipeline detect (not just discourage) a later stage silently altering an earlier stage's output?

### Test immutability and the change-request path

Test integrity rests on three complementary controls, none of them sufficient alone (`GUARDRAILS.md` Test immutability mechanism, contract A4), over four kinds of path Phase 3 now names explicitly: **Protected paths** (every file `tester` created — tests and support alike: fixtures, fakes, recorders, builders, fake clocks, test-profile configuration), **envelope** (pre-existing files the contract depends on, each marked proof-relevant **by effect, never by file type**), **relied-on existing tests** (diffed like envelope files, their execution observed at verification), and **controlled paths** (Protected paths plus proof-relevant envelope files plus relied-on tests — the set every transition patch covers). (1) Byte-identity of Protected paths since the active anchor (`git diff --stat <anchor>..HEAD -- <paths>`, command form unchanged since Phase 1) — any uncovered change is FAIL. (2) An execution-envelope review — the developer may change an *ordinary* (non-proof-relevant) envelope file only when justified in IMPLEMENTATION.md's Envelope changes, and the verifier diffs those files (now including relied-on tests) separately (`git diff --name-status <anchor>..HEAD -- <envelope files>`); a change to a file marked proof-relevant is FAIL whenever no approved amendment covers it, **regardless of any justification offered** — a proof-relevant file is never an ordinary envelope change. (3) The verifier's own contract run confirming, from the tool output itself, that every named test identity — including every relied-on identity — was discovered, executed, not skipped, and reached its classified result; a diff can be clean while a test was excluded from the run entirely, which only this third control catches. The only sanctioned path around all three is the change-request path: on approval of an amendable effect (T12's enum; `REQUIREMENT_CHANGE` is never amendable), `tester` — the sole writer of any amendment delta — applies only the approved delta, commits a **candidate anchor**, and records the full content **transition patch** over every controlled path from the prior anchor (`git diff <prior anchor>..HEAD -- <controlled paths>`, verbatim; a `--stat` companion never substitutes for it); the candidate becomes the active anchor only once `adversary`'s re-review finds the transition patch equals the approved delta and nothing else and `tester`, re-invoked in activation mode, records that outcome — until then the prior anchor remains active and the candidate is not evidence. Ask: is the internal pipeline's equivalent check mechanical (a diff command) or procedural (a code-review rule a human could miss)? Does it check test-file identity, test-*configuration* identity, and actual-execution identity as three separate controls, or does it collapse them into one and leave a gap the others would have caught? Does it distinguish a config file that merely changes a version number from one that silently swaps the storage engine or provider a test observes — and does that distinction follow the file's actual effect, or its type?

### Executable definition of done

Phase 3's organizing idea is that the approved plan's clauses become an **executable, reviewed definition of correctness**, not just a written one: level chosen by the outcome required, never by convenience (T3); the responsible path always real, a double only at an edge to observe or supply a Given (T4); RED reproduced twice at the test's own assertion, not a compile error or an unarranged Given (T6); an **independent test review before any implementation exists** — `adversary` derives required outcomes and plausible incorrect behaviors from PLAN.md alone, before reading test source, then asks whether those incorrect behaviors would pass (T11's outcome-first method); interface evidence kept distinct from local business evidence and from live cross-system evidence, so a field-list agreement is never mistaken for `ESTABLISHED` (T8); an honest `NOT_VERIFIED` clause that caps the Verifier's verdict at `INCOMPLETE` — never `PASS`, and never reaching G4 — rather than a substitute test quietly standing in for a proof it does not give (T10); and an amendment path that may change **how** a test observes but never **what** the approved clause requires, re-reviewed every time and activated only once a content transition patch is shown to equal exactly the approved delta (T12). Ask: does the internal pipeline treat "the tests pass" as sufficient evidence of correctness, or does it require the tests themselves to have been independently reviewed against the requirement before anyone trusts a passing run? Does it distinguish a test that merely runs from one that has been shown to fail for the right reason, twice? When its equivalent of a test cannot execute in the current environment, does it record that honestly as a gap that blocks final sign-off, or does a partial substitute quietly count as done?

### Evidence-bound GREEN and anchored verification

Phase 4 binds the Developer's GREEN claim to one committed HEAD and a complete handoff attempt: clean matching brackets, the unmodified contract command, every contract and relied-on identity observed, a passing full suite, both controlled-path halves, an envelope diff matching declared hunks, and a baseline-to-HEAD inventory with no unrelated path. Reservation-first counters make interrupted executions visible and preserve the same logical-round allowance on resume. The Verifier does not inherit that claim as proof: it derives obligations first, re-runs the contract and suite, inventories and reads the full patch, anchors every blocking semantic finding to an approved element or a narrowly sourced established invariant, and only then reconciles IMPLEMENTATION.md. A test-passing candidate can therefore FAIL for a violated C/Q/I/scope obligation, while unavailable evidence remains neither failure nor success and an implemented `NOT_VERIFIED` clause remains `INCOMPLETE`. Ask: does the internal pipeline bind GREEN to an immutable candidate and independently reconstruct both execution and semantic evidence, or can a passing command or implementation summary stand in for either? When a fix lands, does it re-run every repository and carry prior finding ids forward as `CLOSED` or `OPEN`?

### The verified commit invariant

The exact SHA the verifier tested is the only SHA that is ever pushed. Before any push, `workspace` records the attempt, preflights every selected repository against current G4/verification, resolves read/write identity, and immediately rechecks the affected tuple/ref before the effect. The push names the verified object explicitly; exact-ref rereads establish `CONFIRMED`, while partial/unknown outcomes remain durable for human-confirmed continuation. `pr` repeats local eligibility before MCP, verifies branch A = verified A = G4 A, and checks material PR content plus mandatory post-create state/SHA. These controls do not make remote effects atomic, exactly once, or safe from a race after the read. Ask: does the internal pipeline bind review, publication, and PR content to one current basis while preserving partial effects honestly?

### Facts, assumptions, decisions

Provenance tags (`[JIRA]`, `[REPO]`, `[DEV]`, `[TOOL]`, `[INFERENCE]`) separate a sourced fact from inference throughout every artifact, but Phase 2 adds a second, orthogonal separation on top: the R6 routing rule in `plan-grounding` separates what the planner may proceed on itself (`ASSUMED` — technical, reversible, a concretely recorded consequence) from what only the developer may decide (`G3`) or from what planning cannot resolve on any honest proposal at all (`BLOCKING`). G3 shows the planner's recommendation for every material choice, and a recommendation is explicitly not consent — `pipeline.agent.md`'s G3 wording asks the developer to "accept the recommendation or give a replacement," and any replacement answer is recorded `SEND_BACK`, never folded into an `APPROVE`. A human answer that changes the plan therefore sends it back to a new planning cycle rather than riding on the approval already given to the displayed recommendation. Ask: does the internal pipeline distinguish a tool's recommendation from a human's actual consent as sharply as this — could a displayed-but-unconfirmed default ship because no one explicitly objected to it?

### Human gates and bounded loops

G1–G4 plus the conditional STOP catalogue are all voiced by a single orchestrator, never by a stateless subagent (`FLOW.md` Gates; `GUARDRAILS.md` Human gates and conditional STOPs). Three outer loops are bounded: adversary/planner permits at most two rounds per planning cycle (`ADVERSARY_REVISE_LIMIT` on the second REVISE); test review permits one initial review plus at most one automatic correction (`TEST_REVIEW_REVISE_LIMIT` on the second REVISE); verifier/developer permits one initial verification plus at most two fix rounds (`VERIFIER_FAIL_LIMIT` on the third FAIL). Stage 6 has a separate per-repository, per-logical-round allowance of six contract iterations, two consecutive iterations without progress, six diagnostic runs, and two handoff attempts; limits are checked before a step, and success on the last allowance stands. A `SEND_BACK`, redirect, or directed implementation round is an explicit human decision with its own recorded identity and bounded allowance, never an automatic reset. Ask: where does the internal pipeline place its human checkpoints relative to these four, and are each of its planning, test-review, implementation, and verification loops separately bounded? Do interruptions preserve consumed attempts, or silently renew them?

### Resume by artifact

There is no separate run-state machine — resumability comes entirely from the twelve artifacts on disk, RUN.md's ACTIVE/SUPERSEDED history, current gates, and recorded decisions. Earlier rules still land at stage 2/3/4 for an interrupted planning cycle, stage 5/5b/activation for test recovery, and the same stage-6 round for implementation interruption. Phase 5 evaluates WORKSPACE.md preparation separately from its Publish section: current-basis pending/unknown/failed publication resumes stage 9, and pending/unknown/blocked PR work resumes stage 10, only after a recorded human continuation. Neither path regenerates stage 2 or blindly repeats an unknown effect; changed basis stales G4. Successful `PUBLISH_ONLY` records stage 10 `NOT_RUN`, so absent PR.md is terminal rather than incomplete. Ask: if the internal pipeline's state and artifacts disagree, which wins, and can it resume the earliest unfinished control without erasing known external effects?

## Deferred / known limitations

This design intentionally leaves several things unresolved for Phase 1. Before treating any absence above as a design flaw, check whether it is already listed as deferred: `GUARDRAILS.md`'s Known limitations section (no hard block without hooks, single-root-folder only, Local-harness-only, `<dir>` slot excludes whitespace/shell-special repository names, no concurrent-run locking) and contract §12 Deferred (hooks hardening, quoted-path support, model benchmarks, org-level agent distribution, Agent Host portability, confirming exact Jira/Bitbucket MCP tool names and the model picker string, any runtime resumability beyond artifact presence).
