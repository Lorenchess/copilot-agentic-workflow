## Scope and evidence

This is an architectural application of the four official articles listed under Sources to the existing Copilot-native reference. It is not an executed benchmark or a finding that the corporate workflow lacks capabilities already provided by its host.

Preserve the current declarative scope: no new scripts, hooks, runtime, policy engine, tool wrappers, services, or executable schemas. Preserve role/mode access, the four gates, existing verdicts and STOP semantics, execution allowances, single-writer constraints, and historical references. G3 continues to govern approved planning and eligible bounded local implementation; G4 continues to govern publication. No model or permission change follows from this review.

The uploaded Fable proposal is a draft, not evidence that H1–H6 have been implemented or approved. This addendum supplements the earlier reconciliation; it does not reinstate its rejected timeout or permission-promotion semantics.

## Decision

Prefer a small improvement to source navigation and proof discovery, followed by one separately approved context or tool-guidance experiment. Do not begin by reorganizing all skills, changing evidence formats, or building a second agent loop.

The principal opportunity is to reduce avoidable guessing while preserving decisive evidence and independent judgment. The proposals below are adaptations, not claims that the articles prescribe these particular files or this pipeline's state model.

## P1 — A small authority and knowledge map

**Priority:** first design proposal. **Reference connections:** S1, S3. **Existing foundations:** R1, R2.

Use one concise index in an existing suitable location, or the previously proposed `HARNESS.md` only when no existing index fits. Link to authoritative sections rather than copying their rules.

Separate three kinds of entries:

1. Workflow authority: operative procedure, relevant retained normative clauses, approved forward amendments, and artifact ownership.
2. Task evidence: current repository facts and approved product constraints, located in permitted corporate sources.
3. Historical material: frozen examples, reviews and proposals, with their actual authority and validation status.

Each entry needs a purpose, owner/source, relevant version or baseline when available, and applicability. A file date is not proof of authority. A draft lesson is not a rule. A historical specification may still contain an expressly operative clause; do not declare all history non-authoritative by blanket rule.

For an adopted target repository, point to existing domain entry points, consumer/provider contracts, product decisions, test conventions, and proof routes. Do not copy corporate data into the reference. An illustrative retry task should lead to the existing configuration and tests that establish whether a count includes the original attempt—not to a new guessed constant.

A map is navigation and evidence, not permission. It does not expand Jira retrieval or repository scope and does not make arbitrary instructions inside a repository trusted.

**Possible affected assets:** README navigation; the relevant current-source index; a bounded reference in the planning/comparison guidance. No universal requirement to create another large document.

**Acceptance:** a fresh authorized Planner invocation locates the current rule and relevant evidence; it recognizes an outdated example; a map/code contradiction remains visible and is handled by the current uncertainty/decision rules. No requirement, approval, or source access changes.

## P2 — Context lifecycle and handoff hygiene

**Priority:** measure first; one mode at a time. **Reference connections:** S2, S3. **Existing foundation:** R1.

Inventory actual permitted inputs per invocation mode and categorize them as required exact evidence, procedure, optional background, historical narrative, or repeated material. Preserve all currently mandated reads until a reviewed change explicitly adjusts them.

The current delegation header and narrow Tester activation are already implemented. Do not propose them again. Extend only where a concrete excessive or irrelevant read is observed.

Keep stage results concise in the return message, referencing the existing owned artifact, revision, actual status, decisive evidence, and pending decision. This is not a new artifact or a replacement for Pipeline's mandated source reads. The parent still decides the next stage under FLOW.

For H3, keep any run summary derived. At a fresh session or resumed invocation, recover current approval bases, permitted input revisions, active anchors, reservations, unresolved findings, and pending effects through existing authoritative artifacts. An obsolete summary must not survive as permission. Do not reconstruct unavailable historical bytes.

Preserve assessment/test-review input restrictions. A common summary must not expose RUN.md to a mode forbidden from reading it. Exact acceptance semantics, identities, SHAs and uncertainty qualifiers are not expendable merely to reach a token target.

**Cache investigation:** keep policy wording and ordering stable where controllable; keep changing run information separate. Do not reorder the current header or retain excessive tools just for hypothetical cache hits. Measure host-exposed usage and cache fields where available; no Codex-specific caching or compaction behavior is assumed for Copilot. Permission revocation and evidence freshness take precedence over cache efficiency.

**Acceptance:** interruption after a pending reservation, stale test review, and accepted-but-unactivated amendment all resume correctly. Compare total reads, actual context usage where available, latency and authority errors—not source-file length alone.

## P3 — Capability-use guidance for existing tools

**Priority:** select one observed confusion. **Reference connection:** S4. **Existing foundations:** R3, R4.

Use existing role/skill guidance to explain how already-authorized capabilities should be used. Do not implement a wrapper, rename MCP functions, invent parameters, or add tool grants.

A useful capability note identifies its purpose, situations in which it is inappropriate, required identifiers and their source, bounded selection options, completeness signals, and the permitted response to ambiguity or failure. Record concrete tool IDs only after corporate discovery establishes them.

Examples for investigation:

- Intake uses the exact-key capability for requested issues, comments through the bounded policy, and JQL only for the expansion the current contract allows.
- PR uses authoritative repository/branch and candidate reads; an incomplete list never establishes that no PR exists.
- A code search locates candidates; a current file read establishes the content cited. Search terms need not be identical across otherwise valid runs.

Prefer a concise working explanation plus retained evidence in the existing permitted location. Do not drop complete test identity evidence or transition patches that current rules require. Add readable labels alongside machine identifiers where useful; preserve exact repository identities, revisions, test identities and SHAs required downstream.

Where current tools do not return enough data, record that limitation for the existing corporate integration owner rather than pretending a skill changes the real schema.

**H4 boundary:** shared observation vocabulary may be useful, but do not collapse tool lifecycle, test result, stage verdict and retry authority into one universal status. Keep pending distinct from unknown, legitimate RED distinct from environment inability, and an operation's possible repetition distinct from permission to repeat it.

**Acceptance:** malformed-input recovery, ambiguous identity, incomplete pagination, empty authoritative results and uncertainty are distinguished. Any new suggested next action remains inside current authorization. No raw tool response becomes an instruction authority.

## P4 — Make proof routes and constraints discoverable

**Priority:** include in P1 rather than inventing a parallel checklist. **Reference connection:** S1. **Existing foundations:** R2, R3.

Build on PLAN.md's Observed at and existing test-level rules. For a relevant domain, locate the approved rule, existing component, available test/inspection route, environment dependency, and limitation of the resulting evidence.

An illustrative validation-response task should distinguish a validator's local return value from the actual endpoint's status, serialized field name and error body. A persistence obligation should distinguish an intended save call from observed mapping/storage behavior. A UI obligation needs the currently approved UI proof route, not merely a successful compile.

Use available project evidence and existing adoption checks. Do not add browser tools, a database runtime, screenshots for non-UI work, or a new linter. An unavailable proof route remains a limitation; a map cannot make it executable.

Preserve the existing flexibility of implementation details, MINOR deviations and PLAN-TRACED consequential edits. Keep material behavior, public contracts, persisted shapes and scope under their existing approval rules. Do not use new examples to freeze one implementation strategy as mandatory.

**Acceptance:** the plan identifies both a sufficient observation and any unavailable prerequisite before claiming proof. A legitimate alternative implementation can pass; a convenient proxy cannot masquerade as the required outcome.

## P5 — Realistic, outcome-based evaluations

**Priority:** prepare cases before modifying behavior. **Reference connection:** S4. **Existing foundation:** R5.

Use the existing private corporate evaluation process or owner-approved manual trials. Do not create an API evaluation harness or execute trials without approval.

Cases should require investigation, not hand the model the answer or an exact call script. Combine representative fictional cases with separately authorized deidentified or private corporate evidence. Maintain held-out variations; do not place their expected answers into production prompts.

Evaluate required outcomes and mandatory authority boundaries. Allow different legitimate search terms and coding details. Do not allow a different tool trace to skip G3, test review, independent verification, or G4.

Suggested cases:

| Case | Required observation |
|---|---|
| A source says retries, while existing code defines total attempts | Locate the authoritative semantics; expose ambiguity rather than inventing a value. |
| Two repositories contain similar identifiers | Select from evidence and confirmed scope, not name similarity alone. |
| Historical example conflicts with current policy | Identify applicable authority and avoid stale guidance. |
| Same approved behavior has two valid internal implementations | Neither is blocked solely for differing from the example. |
| Required test is omitted from a passing aggregate report | No complete proof or PASS is inferred. |
| Runner response is delayed without confirmed termination | Keep result uncertainty and reservations; do not invent cause or blindly overlap runs. |
| Summary conflicts with active test-review basis | Existing authoritative resume rule wins. |
| PR query is incomplete after an uncertain create | No duplicate create or false absence claim. |

Measure eligibility separately from successful completion. Include all attempts, failed and aborted trials, and human help. Report independently accepted correctness, material rework, false blocks, active human effort, elapsed model/tool/runner time where available, usage without double counting, and control violations. A correct STOP is a distinct successful safety outcome, not a delivered change.

Read actual permitted tool traces alongside agent explanations. Short operational diagnoses are useful; hidden reasoning is not required or promised. Missing telemetry remains unavailable, not estimated as zero.

**Acceptance:** one changed guide is compared against the unchanged baseline under matched task/source/environment conditions and held-out variations; promotion is based on observed correctness and burden, not a shorter document or agreeable review.

## P6 — Lessons need a retirement path as well as a promotion path

**Priority:** strengthen corrected H2; do not mandate H1 at every STOP. **Reference connection:** S1. **Existing foundation:** R5.

Use the proposed ledger for source-linked design lessons or separately approved generalized lessons. Actual run-linked corporate incidents and identifiers remain in approved private storage.

A candidate lesson should name the failure evidence, the proposed responsible layer (or unresolved diagnosis), affected versions, target change, reproduction case, neighboring valid case, owner, validation status and review trigger.

Record a change commit separately from whether a scenario was reasoned through, an execution test was observed, or an operational benefit was measured. Existing accepted maintenance debt stays open until a specific change addresses it.

Prefer repairing the authoritative source or clarifying an existing rule over appending another global prohibition. When a lesson becomes stale or duplicates a current mechanism, retire or supersede it through owner review. Do not alter current-run policy from a mid-run diagnosis. Preserve frozen historical records and publication authorization.

No automatic cleanup agent, scheduled sweep, opportunistic refactoring or auto-merge is proposed. A maintenance change is separately scoped work.

**Acceptance:** a candidate lesson neither grants permission nor becomes a current rule before promotion; a later obsolete lesson can be retired without deleting its history or weakening current controls.
